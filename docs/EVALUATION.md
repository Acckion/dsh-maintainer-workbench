# 可复现工作流评估与演示

## 这套评估回答什么

对同一组受控输入，工作台是否正确完成阶段交接、保留执行证据、拒绝错误产物，并支持恢复？它直接运行归档基线和当前源码，不比较两份手填报告。

**这是确定性工作流契约评估，不是真实模型能力或维护成功率评测。** 执行器/模型返回值由夹具规定；真实本地 Git 工作区、补丁、子进程回归命令、存储和核心工作台逻辑仍会运行。

## 从源码运行

要求 Node.js 24+、Git、tar，以及 `npm ci` 安装的固定依赖。默认基线提交是 `853bc5a75cc2823e407d8a0a6123cabca85d3985`，必须存在于本地 Git 历史。

```sh
npm run check
npm run evaluate
# 仅重放核心工作流契约，明确跳过原生宿主联调：
npm run evaluate -- --skip-native
# 指定其他可比较的本地提交和新的空输出目录：
npm run evaluate -- --baseline <commit> --out .data/evaluations/my-run
```

基线以 `git archive` 解压到临时目录，当前源代码保持不变。两侧必须拥有完全相同的依赖锁文件；否则比较中止，避免把依赖升级混进代码效果。输出目录必须为空，防止不同次运行的证据混放。每次运行保留代码提交、工作区是否存在未提交修改、语料版本及 SHA-256、依赖锁 SHA-256。

核心语料进程用本地响应替身处理模型/GitHub 请求，其余 fetch 默认拒绝；不读取真实 API Key。原生联调使用隔离的 DSH_HOME、本地 Messages 服务和占位凭据。不会发布评论、标签、PR 或支付模型费用。宿主固定端口 4320，运行时不要并发启动另一份原生夹具；原有正常用户工作台不应使用该测试端口。

## 八个案例与判定依据

| 案例 | 观察与判定 |
|---|---|
| bug-lifecycle | 分诊→调查→实施→验证→独立审查；真正的 Node 测试先失败后通过；四个代码阶段工作区不同；原始仓库不变 |
| clean-review | 正确代码通过验证；受控审查返回零发现、零补丁 |
| missing-context | 缺少证据时保留 needs_info，不创建代码工作区 |
| mutation-retry | 验证器越界修改代码后，初次执行和重试均不能交付违规产物 |
| unexecuted-test-claim | 远端纯分析输出臆报 passed 时，阶段产物、兼容结果和后续交接均为 not_run |
| binary-handoff | 二进制新增、修改、删除跨实施/验证/审查逐字节一致，原始文件不变 |
| unsupported-duplicate | 提供范围外的重复 Issue 编号必须被拒绝 |
| format-recovery | 真正的格式失败可以整理，实施仅发生一次，补丁保持一致 |

负样本使用脚本化响应，只是验证错误/无缺陷情况下的产品行为，不能据此给出真实模型误报率。

## 输出与复查

- `baseline.json`、`candidate.json`：每个案例的期待、实际结果、错误、运行耗时、执行器调用数、实际测试命令/退出码/输出、阶段产物和补丁
- `comparison.json`：代码与语料版本、依赖指纹、逐案例比较、汇总和未测指标
- `native.json`：原生 Harness 联调状态。即使跳过也写入 not_run
- `native.log`：仅运行原生联调时存在；本地登录 token 在保存前隐去
- `SUMMARY.md`：可阅读摘要，保留失败案例，不只展示成功结果

当前源分支若有未提交修改，报告会显式标记；正式留证应先提交再运行。

`npm run evaluate` 默认另外运行已有原生夹具，实际覆盖 fix 和 triage 两种宿主路径，使用真正的 Harness Agent / shell 和本地脚本模型。八案例的完整阶段重放使用确定性测试执行器。不要把前者两阶段的原生验证说成八案例均经过真实模型推理。

## 下一步真实模型验收

真实模型验收仍未完成。需先确定并批准 provider、model、reasoning、凭据配置目的地、预算上限和可读写的测试仓库，再在固定提交与相同输入上比较基础工作流和工作台。

应分开记录：有效定位、修复前失败/修复后通过、无关修改、无法复现、无缺陷 PR 的误报、维护者采纳、实际工具证据、真实 token/费用、墙钟耗时。保留失败样本，并由团队审核结果，不能让同一模型自行给自己的结果打最终分。没有实际采样前，不填写成功率或竞品领先结论。
