# 事项工作流编排实现记录

日期：2026-10-09。设计与验收依据为 [工作流编排计划](WORKFLOW-ORCHESTRATION-PLAN.md)。

## 已接入的流程

分诊、PR 预检和调查报告现在可以返回带来源的计划草稿。草稿包含目标、范围、验收、类型专属字段、推荐路线与缺口。历史报告缺少草稿时先重新整理材料；未生成完整信息的报告保留缺口，不自动编造验收条件。

维护者确认后，当前处理周期保存计划版本、输入身份、执行授权、步骤预算与检查点。代码或文档实施产生补丁后自动进入独立验证；必需验证通过后进入独立补丁审查，最后等待维护者审核。调查完成后提供更新草稿供核对。验证失败按类型给出恢复建议，不自动修代码或修文档；审查发现不自动触发修改。

编排调用现有队列、阶段产物、工作区、补丁交接和证据检查。重复确认复用进行中的授权；输入或已确认计划变化阻止继续。取消停止后续自动推进并保留产物，暂停允许当前任务结束。进程中断的执行保持失败，必须检查现场后明确重试；完成产物到下一步骤的检查点可以恢复，不静默重放状态不明的修改。

PR 审查意见经预览确认发布后，可等待作者新提交。新 head 触发重新预检和审查，保留历史发现供复核；相同 head 不重复派发。已有预检与计划足够时，仓库可开启只读自动审查，默认关闭，不自动修改或发布。原有创建草稿 PR、更新原 PR 和补丁导出继续使用各自的版本、证据与权限检查。

## 计划确认与补充信息

计划批准由维护者在计划草稿界面完成一次。模型的 `inputRequest.fields` 可标注 `purpose: information / decision / plan_confirmation`；资料缺失和实质取舍仍保存为输入等待。分析报告具备完整目标、范围、验收及可执行路线时，纯计划确认转交界面，不授予执行权限；混合请求只移除确认字段，保留真实问题。兼容旧报告只识别明确的 `confirm_plan` 实施确认，不依据泛化关键词取消问题。文件是否存在和锚点检查属于系统后续检查，提示模型不将其当作人工资料缺口。

对当前周期、当前材料的既有分析报告，可恢复误建的纯计划确认等待。原请求以取消事件保留，草稿待人工确认，既不调用模型，也不启动实施或自动审查。缺少完整草稿、真正信息请求、已授权执行、跨周期及过期报告不自动恢复。

## 界面

- 详情默认显示系统建议、计划草稿或事项进度；草稿可直接确认或修改，来源和缺口可查看。已有草稿时不再同时展示“尚未分析”提示，历史结论仍保留。
- 分诊、调查、实施和验证等单独阶段收进高级操作，保留原有入口及门槛。
- 补充回复在主区域显示，核对后重新评估；等待外部和执行中状态不占用人工决策队列。
- 首页按待确认计划、需要补充或解除阻塞、待最终审核展示事项，并可直接定位详情。
- 执行列表按事项聚合，运行记录及来源关系保留在事项内。
- 批量入口先分析所选事项，展示逐项范围和验收，再按建议开始；新建、复用、跳过与失败逐项展示。
- 最终审核继续复用五部分概览及发布预览，不自动批准中间报告或执行远端发布。

## 与 master 重构的整合

沿用 master 的领域类型、纯事件状态机、SQLite 处理周期、应用服务、执行器与工作区管理。`application/orchestration.ts` 是计划授权和自动阶段交接的应用协调服务；`core/workbench.ts` 继续只组合服务，`core/orchestration.ts` 仅保留兼容导出。事项生命周期、等待、输入、历史和版本冲突仍由 master 的处理周期负责，界面的建议状态单独投影，不能覆盖 `Issue.processing`。

计划状态统一保存在 `ProcessingCase.planning`，每次变化通过纯状态机的 `planning.recorded` 事件落盘；`Issue.orchestration` 为兼容投影，事项表不保存第二份状态。启动时迁移旧计划与检查点，不执行任务；旧授权缺少周期绑定时阻塞供核对，重开事项的旧计划仅留在历史周期。重复保存不产生额外事件，过期版本或跨周期授权写入拒绝并回滚。

确认和批量确认沿用后端版本冲突保护。批量入口只启动待确认计划；执行中、待最终审核、待外部回复及阻塞事项不会混入正常批量启动。处理历史用可读名称展示事件，并展示所选周期的目标、范围、进度及当前步骤。已消费中间产物交接后结束其审核等待，最终审核和输入/环境等待保留。

任务绑定当前处理周期和执行授权。master 原有 resolve 目标交接继续可用；计划授权任务由协调服务推进，同一任务不会同时进入两种自动交接。任务恢复仍复用 TaskService，等待输入或环境时保留原运行，确认计划不能覆盖未回答的输入请求，关闭后重开的旧周期也不能继续执行。

保留 Overview / Plan / Work / Review、Summary / Activity / Diff、深色主题、输入与环境恢复、草稿持久化以及工作区检查与清理。随后合入 master 新增的原生 Harness 全局设置入口、设置并发冲突保护，以及从有未提交修改的源目录运行固定提交隔离任务的能力，源目录和暂存区保持不变。系统建议和高级操作嵌入现有面板；建议修订复用 `item_drafts`，并绑定材料指纹，刷新恢复草稿，材料变化时重新确认。仓库整理入口与原有目标处理能力保留。

## 第二轮文档事项试用

1. 打开此前第二轮 Issue #3，在 Triage 或概览中点击“开始处理”。历史分诊没有计划草稿时，系统会重新整理材料。

4. 正常路径结束后到 Review 查看最终审核。遇到文档错误、环境问题或缺证据时查看具体原因，选择对应恢复，原失败报告保留。
5. 审核并选择具体交付预览。接受本地产物与对外发布仍分别确认；本轮不会自动合并或关闭 Issue。

真实模型在原 Issue #3 上的计划准确性、完整执行和实际人工操作负担仍需这次用户试用验证。自动修复审查发现、全面求值远端合并规则及精确费用预算保留后续。既有运行记录的高级入口继续可用，不通过删除历史减少界面数量。

### 验收列表格式恢复

文档实施报告中的 `acceptanceCriteria` 必须是字符串数组。若结果整理模型输出了非空的“验收项 → 文本或 null”映射，宿主只把已有文本逐项转换为列表，再执行完整阶段结构校验，并记录恢复提示。嵌套对象、布尔值、空映射、缺失字段或错误的 tests 结构仍失败；不会改写原始输出，也不会根据验收文本生成测试成功证据。原始输出若仍为非法 JSON，继续走既有禁止工具的格式整理路径，不重新实施文件修改。

### 明确恢复后的预算续期

维护者从当前任务重试、补充输入后继续或恢复可继续的步骤时，先核对处理周期、计划与输入版本，再为同一计划续期并记录 `workflow.budget_renewed`。新的截止时间使用当前仓库超时预算的四倍，并为后续推进预留最多六个新的阶段任务；原始开始时间、计划授权、已完成任务与失败记录保留。自动完成事件、重启核对及重复事件不续期。旧任务不再是当前步骤、版本或计划已变化时，恢复在派发之前拒绝。报告已完成但因预算过期停止的 docs/fix 从现有产物进入 validate，再按原有检查门禁进入 review，不重新实施修改；真正失败的任务仍使用明确重试路径。

### 文档验证的必需与补充证据

文档检查器的同 Session、同版本、同补丁记录先绑定，再进行通用命令证据核对，避免命令后附退出码输出时产生残留的虚假阻塞。文档补丁验收以宿主四项必需检查为准；模型额外报告的探查、未请求的构建等放入补充证据，并仅在精确关联执行记录时标记通过。明确要求的额外命令继续参与验收，真实模型阻塞保留。额外描述不能取代必需检查，也不能因报告省略命令内容而制造额外验收门禁。缺少必需记录、补丁/Session 不符或检查失败仍阻塞。本次 Issue #4 的错误阻塞根据保留的、经当前补丁哈希复核的执行记录纠正并记入审计，未重跑模型，原始报告保留。
