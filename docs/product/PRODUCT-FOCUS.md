# 维护工作台的产品边界与个人试用目标

版本日期：2026-10-02。本轮基线为 `d4bb34c`，工作分支为 `feat/unified-review-evidence`。

## 为谁解决什么问题

面向同时维护多个 Issue、PR 和修订任务的个人或小团队维护者。核心工作不是再开一个聊天窗口，而是在有限精力下判断：什么值得处理、为什么这样判断、执行卡在哪里、哪份结果值得接受。

工作台承担资料分诊、阶段编排、证据归集和明确的交接。维护者决定优先级、接受或退回结果，并确认具体的外部发布。AI 的结论、测试报告和真实执行证据不能混成一个“成功”标签。

## 一条完整的使用路径

1. 接入已有仓库，批量分诊。对缺信息的问题先提出补充要求；对具体缺陷列出影响假设和调查依据。
2. 调查与实施在固定版本运行。维护者能看见当前状态、最近记录、等待原因和原生会话；中断后仍能检查原记录并明确选择重试。
3. 全量验证暴露失败时返回修订，不能因为报告生成成功而把事项标成已解决。
4. 审阅时在一个入口看到当前结论、补丁范围、同一补丁的验证报告、已知限制与待处置发现。需要细看时直接打开对应产物和证据。
5. 接受独立审查后回到精确实施产物；接受本地产物与对外发布仍为不同动作。远端版本或补丁变化后须重新核验。

## 本轮只补统一审阅这一处断点

安装包试用已经验证维护流程可运行，但审查产物本身没有 tests 字段；回到实施任务后，前序独立验证、审查结论和实施限制又分散在历史中。维护者需要重新拼接证据，容易把旧报告或局部测试当作当前补丁的验证。

本轮默认详情增加精简的审阅摘要：当前状态与下一步、当前结论、修改范围、明确标注来源的验证报告、风险和限制。它只沿明确的来源链引用相同事项、版本、基线与补丁的记录；缺失、过期或不匹配时显示未确认，不在同事项所有历史中挑一份通过结果。摘要不代替完整 diff、工具日志或后端发布核验。

同时修正接受按钮的措辞与过期禁用状态，让“接受此报告”不被误读为“代码已通过全部验证，可以自动发布”。失败时保留原始输出和明确恢复方式，不自动重跑。

## 个人试用版验收目标

| 场景 | 本轮应达到的状态 |
|---|---|
| 缺信息分诊 | 首次打开就能看到缺什么、影响哪些判断、为何暂不实施；不虚构代码或测试证据 |
| 执行等待或失败 | 状态、已记录原因、保留的证据与适用恢复方式清楚；不会承诺不存在的进度、费用或审批状态 |
| 部分修复验证失败 | 当前补丁对应失败报告可见，能够返回修订；旧通过结果不能覆盖失败 |
| 完整修订审查 | 同一入口显示补丁、独立验证、审查结论和实施限制；一条明确操作即可打开指定来源的详情或证据 |
| 输入或交接变化 | 来源缺失、错事项、错版本、不同补丁、循环交接与过期记录均显示无法确认；不会误呈现可交付状态 |

“同一入口”和“一条操作”是交互设计与组件自动测试目标，尚不是已测的人为点击次数。继续使用原十步安装包回放确认接入没有退化，不扩充语料来制造模型效果提升。

## 不做什么

本轮不做自动合并、无人确认发布、新的模型接入、通用 IDE、完整 Git 客户端或更多管理仪表盘。不改宿主固定兼容目标，不借预览限制创建另一个网站冒充原生插件。

达到组件/状态回归、安装包回放和可复现交付后停止扩展，交给维护者亲自验证入口是否清楚、证据是否够用、状态是否可信。云端浏览器可视验收仍受限；真实模型质量、费用和人工效率需要另行授权及测量。
