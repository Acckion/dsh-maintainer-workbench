# 维护工作台的产品定位与设计边界

定位修订：2026-10-26。本次只更新文档；以下产品目标不代表新增功能或新的效果验收。2026-10-02 的统一审阅迭代记录保留在后半部分，不能作为当前版本的完整状态说明。

## 当前产品定位

面向个人和小团队开源维护者，帮助他们在有限精力下接住社区反馈和代码贡献。维护者需要知道哪些事项值得处理、当前工作卡在哪里，以及哪些修改有足够依据进入最终审核。

工作台以 DeepSeek Harness 原生插件提供。AI 负责理解非结构化反馈、调查问题、提出计划和完成授权范围内的修改；工作台组织处理周期、执行交接、实际证据和最终决定。用户在确认范围、补充必要信息、处理异常和接受交付时介入。

产品价值目标是减少重复查证、减少把不完整结果当作完成的误判，并保留中断后的上下文。这些是待真实使用测量的目标；现有回归通过数不证明节省了多少时间、提高了多少修复率。

## 设计重点与当前范围

| 设计重点 | 当前已有基础 | 仍需完善或验证 |
|---|---|---|
| 清楚地决定下一步 | 事项计划、阶段进度、等待原因、最终审核与历史记录 | 首屏对非技术读者的解释、真实维护者能否快速判断下一步 |
| 结果带着对应证据 | 同事项、版本、基线和补丁的验证与审查关联；缺失或过期保留未确认 | 实际测试的充分性、模型推理正确性、人工审阅负担 |
| 中断后可以交接 | 持久化处理周期、输入、失败记录和显式恢复 | 更多真实中断、多人交接及长期使用场景 |
| 维护者保留决定权 | 计划确认、产物审核、外部发布预览与确认分别处理 | 避免重复确认，核实实际人工介入次数 |
| 开源社区能够复用 | 插件源码、工作流、评估脚本、测试与工程说明 | 最终可访问成果、简短上手路径、外部采用与维护安排 |

证据关联证明的是来源与执行关系，不自动保证推理正确或测试覆盖完整。UI 中的完成、通过、接受、发布应继续分别描述，不能合并成一个含义不明的成功状态。

## 当前入口与待实施的体验建议

当前 [客户端入口](../../src/client/App.tsx) 默认进入当前仓库的问题列表，导航包括 Issues、Pull Requests、Repository 和 Tasks。跨仓库待决策首页、恢复产品说明文字和四问决策卡属于后续体验建议，尚未因本次文档修订成为默认界面。

后续设计首先让事项回答“用户要解决什么、AI 做了什么、实际核实了什么、现在需要谁决定什么”。命令、日志、差异与版本指纹保留在可展开的证据层。首次出现 Issue 和 PR 时可解释为问题反馈和贡献者提交的代码修改。

展示侧聚焦一条完整维护案例，说明维护者与报告者、贡献者如何协作。待验证的核心收益是维护者更容易接住贡献、给出有依据的反馈和完成交接，不以聊天次数、阶段数量或模型数量替代价值。

## 当前优先级

1. 整理最终版本与证据索引，明确历史工程验证、真实试用和待测指标。
2. 用代表性真实问题验证维护者判断与交付，保留失败和未完成事项。
3. 在真实试用反馈基础上改善首屏、决策摘要和首次使用说明。
4. 完成可访问成果、复现说明、许可披露与维护计划。

近期保持维护工具的明确范围，不扩成通用 IDE、完整 Git 客户端或自动合并平台。参赛设计、演示、对照方法和建议状态见 [设计与演示方案](../competition/DESIGN-AND-DEMO.md)，提交材料与规则见 [参赛准备状态](COMPETITION-READINESS.md)。

## 历史迭代：2026-10-02 统一审阅与个人试用

下文为当时的基线 `d4bb34c`、工作分支 `feat/unified-review-evidence` 的迭代记录。“本轮”和“尚未”仅指当轮，不覆盖后续开发；真实浏览器与宿主记录应结合 [证据索引](../competition/EVIDENCE-INDEX.md) 判断。

## 为谁解决什么问题

面向同时维护多个 Issue、PR 和修订任务的个人或小团队维护者。核心工作不是再开一个聊天窗口，而是在有限精力下判断：什么值得处理、为什么这样判断、执行卡在哪里、哪份结果值得接受。

工作台承担资料分诊、阶段编排、证据归集和明确的交接。维护者决定优先级、接受或退回结果，并确认具体的外部发布。AI 的结论、测试报告和真实执行证据不能混成一个“成功”标签。

## 一条完整的使用路径

1. 接入已有仓库，批量分诊。对缺信息的问题先提出补充要求；对具体缺陷列出影响假设和调查依据。
2. 调查与实施在固定版本运行。维护者能看见当前状态、最近记录、等待原因和原生会话；中断后仍能检查原记录并明确选择重试。
3. 全量验证暴露失败时返回修订，不能因为报告生成成功而把事项标成已解决。
4. 审阅时在一个入口看到当前结论、补丁范围、同一补丁的验证报告、已知限制与待处置发现。需要细看时直接打开对应产物和证据。
5. 接受独立审查后回到精确实施产物；接受本地产物与对外发布仍为不同动作。远端版本或补丁变化后须重新核验。

## 本轮只补统一审阅这一处断点

安装包试用已经验证维护流程可运行，但审查产物本身没有 tests 字段；回到实施任务后，前序独立验证、审查结论和实施限制又分散在历史中。维护者需要重新拼接证据，容易把旧报告或局部测试当作当前补丁的验证。

本轮默认详情增加精简的审阅摘要：当前状态与下一步、当前结论、修改范围、明确标注来源的验证报告、风险和限制。它只沿明确的来源链引用相同事项、版本、基线与补丁的记录；缺失、过期或不匹配时显示未确认，不在同事项所有历史中挑一份通过结果。摘要不代替完整 diff、工具日志或后端发布核验。

同时修正接受按钮的措辞与过期禁用状态，让“接受此报告”不被误读为“代码已通过全部验证，可以自动发布”。失败时保留原始输出和明确恢复方式，不自动重跑。

## 个人试用版验收目标

| 场景 | 本轮应达到的状态 |
|---|---|
| 缺信息分诊 | 首次打开就能看到缺什么、影响哪些判断、为何暂不实施；不虚构代码或测试证据 |
| 执行等待或失败 | 状态、已记录原因、保留的证据与适用恢复方式清楚；不会承诺不存在的进度、费用或审批状态 |
| 部分修复验证失败 | 当前补丁对应失败报告可见，能够返回修订；旧通过结果不能覆盖失败 |
| 完整修订审查 | 同一入口显示补丁、独立验证、审查结论和实施限制；一条明确操作即可打开指定来源的详情或证据 |
| 输入或交接变化 | 来源缺失、错事项、错版本、不同补丁、循环交接与过期记录均显示无法确认；不会误呈现可交付状态 |

“同一入口”和“一条操作”是交互设计与组件自动测试目标，尚不是已测的人为点击次数。继续使用原十步安装包回放确认接入没有退化，不扩充语料来制造模型效果提升。

## 不做什么

本轮不做自动合并、无人确认发布、新的模型接入、通用 IDE、完整 Git 客户端或更多管理仪表盘。不改宿主固定兼容目标，不借预览限制创建另一个网站冒充原生插件。

达到组件/状态回归、安装包回放和可复现交付后停止扩展，交给维护者亲自验证入口是否清楚、证据是否够用、状态是否可信。云端浏览器可视验收仍受限；真实模型质量、费用和人工效率需要另行授权及测量。
