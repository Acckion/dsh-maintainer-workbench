# 缺口与阶段推进实施计划

## 目标

沿用现有处理周期、等待、执行、验证、审核与交付机制，统一缺口责任和阶段门槛。维护者确认范围不等于提供复现证据；补充资料不扩大既有授权。

## 实施顺序与验收

1. 增加结构化缺口：资料、系统检查、环境、外部等待、维护者决定、旧记录待归类。记录状态、责任、阻塞阶段、解除条件和来源。保留旧 missingInfo 输入，旧文字保守展示为待系统归类，不猜测责任。
2. 统一路由与门槛：只读范围不能派发 fix/docs；复现资料为空或明确未知不能进入缺陷修复。系统检查未完成不得报告阶段完成；调查有结论后停止并提交实施计划，资料等待不伪装成修复失败。现有补丁验证和独立审核证据规则继续生效。
3. 区分计划确认与事实输入：所有阶段的明确计划确认问题交回计划界面，不能当成实施授权。系统检查不能成为人工必填项。人工请求可区分报告者资料和维护者取舍。
4. 支持部分答复：未知、无法提供、等待报告者都是有效记录但不是已获得证据。保留已填答复和未解决项；仅必需资料满足时解除等待。保存不自动扩大授权或自动重新执行。
5. 界面按责任展示缺口和系统待办，默认展示已有复现摘要；保留高级修订。补充表单显示已有答复、资料状态、请求对象及阻塞项。
6. 验证：确定性测试覆盖 Issue #1 只读路由、系统检查不转人工、部分/未知答复、可选问题、重复确认、版本冲突、既有授权与历史记录；浏览器夹具覆盖缺口分区、部分保存和恢复输入。完成类型检查、完整测试和构建。

## 阶段结束规则

分诊输出事实和路径建议；调查完成授权检查后输出实施建议或具体外部等待；实施产生可追踪补丁后进入验证；必需验证通过后进入独立审核；审核汇总后等待最终人工审核；交付继续区分新 PR、更新 PR、补丁和交给作者。未解决项仅阻塞其声明阶段，不要求所有阶段前置条件在分诊时全部满足。

## 边界

不改 Harness 真实目录成员，不回写现有 Issue #1 记录，不发布追问或调用真实模型验收。结构化缺口由模型建议、后端校验；来源文字不能替代真实验证证据。无需此次改造之外的新调度器或自动 GitHub 写入策略。

## 实施结果（2026-10-10）

以上六项已接入现有契约、执行器和界面。旧记录的文字缺口保守展示为待归类，未进行自动迁移；未标记责任的历史问题仍沿用原等待规则。明确只读的范围进入调查，未知复现条件禁止进入修复。调查保存结论与资料等待分别展示，资料答复不授予新的实施范围。

同版本、同问题、同责任的已提供答复进入后续上下文并去重；部分答复及未知状态持久保存，只有必需问题齐备才解除等待。系统检查未完成时保留报告并阻塞，不生成必填表单。环境和 CI／作者修订复用现有等待记录；外部等待使用宿主记录的版本绑定。调查额外设置 60 次查阅／命令预算，预算用尽保留记录并阻塞，不能算阶段完成。

验证已通过：397 项自动测试、类型检查和构建；缺口表单、阶段时间线、维护流程浏览器夹具在 1440px 和 390px 通过。缺口夹具验证部分保存、刷新恢复、可选项、未知项仍等待、补齐后解除等待且不自动执行。未重跑真实 Issue #1，未验证真实模型质量或远端 CI／作者提交的完整回流。现有任务与历史授权不回写，新任务采用新契约；原有开放等待仍须先处理或结束。

## 分诊输出格式兼容（2026-10-10）

人工问题标识允许 ASCII 连字符，与缺口标识一致；保留长度、唯一性和保留属性名校验。未解决缺口允许空解除条件，界面明确展示「解除条件尚未明确」，原状态、来源与阻塞阶段不变。已解决缺口仍要求非空解除条件和来源；不从空值推断完成。计划未单独输出结构化缺口时继承同一报告的缺口，分诊／预检在等待资料时也展示已保存草稿，等待和授权分别保留。
