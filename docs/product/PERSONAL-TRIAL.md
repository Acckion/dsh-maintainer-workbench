# 维护工作台个人试用说明

本版目标不是增加功能数量，而是让维护判断更清楚：看见问题与依据，知道执行卡在哪里，再决定是否接受哪一份代码。产品边界见 [产品定义](PRODUCT-FOCUS.md)。

## 这一版改了什么

默认任务概览加入统一审阅摘要。当前结论、覆盖范围、修改规模、实施限制、验证报告、审查结论与精确来源入口放在一起；长命令输出和环境说明可以展开。列表区分验证报告失败、不完整和本地接受，不再用一个成功状态掩盖这些差别。

摘要沿明确来源关系核对事项、版本、基线和补丁。原审查引用的验证与其他同补丁报告分开标记：即使审查此前已接受，后来出现同一补丁的失败验证，也会提示重新核对。不同补丁或旧版本的通过记录不会拿来充数。实施自报测试始终与独立验证分开。

排队、等待、失败、取消和仅整理输出等状态给出适用下一步。打开证据、补丁、关联审查或 Harness 会话时带着精确目标，不用凭任务标题重新搜索。过期产物真正禁用接受按钮；接受报告仍只保存本地决定，不自动发布。

## 建议按这五件事试

1. **选一条缺信息的问题。** 看分诊结果是否清楚列出缺什么、影响哪些判断、为什么暂不实施。资料不足时不应虚构根因、代码位置或测试结论。
2. **看一项等待或失败任务。** 不打开原始 JSON，能否判断该去处理会话审批、检查日志、补齐条件，还是重新执行？格式整理重试与重新运行代码应可区分。
3. **看“局部测试过了、完整验证失败”的情况。** 失败必须留在眼前；实施限制和验证报告需要同时可见，不能因为接受过报告就显示为绿色通过。
4. **看完成修订后的审阅。** 能否在当前概览确认这份补丁引用了哪份验证和哪次审查？点击对应证据后，目标应保持一致。其他同补丁报告不得被悄悄藏起来。
5. **检查接受与发布的边界。** 接受本地产物不会自动发评论或推送代码；查看发布预览后仍由你决定。不要为了试界面而向重要仓库写入内容。

最有价值的反馈不是“好不好看”，而是：哪一步让你不知道接下来做什么；哪项结论你不敢相信、还缺哪种证据；哪次跳转让你丢了上下文。记录事项编号、任务短 ID 和现象即可；截图中请避开令牌、私人资料和不相关内容。

## 安装与测试范围

仅在已验证的 Harness `0.1.7-alpha.1` 目标下试用。安装包接受共享宿主 Cordis `4.0.3` 至 `<4.1.0`；此次全新安装实测为 `4.0.4`，开发锁仍是 `4.0.3`。新版 Harness `0.2.0-rc.2` 是另外保存的兼容性试验，不当作本版的完整支持承诺。

在自己的已有 Harness 环境，可通过 Plugins 安装交付的本地 tarball，或使用官方 `dsh plugin --profile web add /absolute/path/to/package.tgz`。完整隔离安装与回放步骤在交付包 `START-HERE.md`；不要把云执行器的 localhost 链接当作你电脑上的应用地址。

先选自己有权限的测试仓库或可丢弃示例。真实模型任务会按所选服务计费，应先自行确认模型、数据发送范围和可接受成本；输出 Token 上限不是总金额预算。当前工程回放使用本地脚本提供方，不需要付费模型，也没有真实 GitHub 发布。

- 精确来源、失败/未执行/阻塞、旧版本/撤销、额外失败验证、覆盖说明、按钮目标及真实 disabled 状态有自动断言
- 云浏览器仍拒绝本地页面访问，未重试被拒地址。本轮没有真实浏览器视觉验收，也没有测量你的点击次数、理解时间、模型正确率或费用

因此，本版达到的是“可安装、可回放、可交给维护者亲测”的工程门槛；入口是否顺手、证据是否够用、状态是否容易理解，仍以实际使用反馈为准。暂不继续增加新的产品模块。
