# Issue 分类与分类型处理流程

日期：2026-09-26。状态：**详细产品设计，待分阶段实现**。

本文件细化 [总体流程](./WORKFLOWS.md)，不能作为已实现功能清单。当前已有 `bug / feature / docs / question / maintenance` 分类及通用阶段；类型专属表单、需求决策、答疑、等待恢复和验收契约尚未完整实现。当前能力以 [实现记录](./IMPLEMENTATION.md) 为准。

## 1. 产品对象与基本原则

用户管理的是一件需要处理的事项，而不是一串 Agent 会话。每次分析、讨论、决策、补丁和 PR 都归属于事项，并保留来源、版本、适用范围和交接关系。

不能把“识别为 Bug”解释为“确认存在缺陷”，不能把“Feature 已接受”解释为“已排期”，也不能把“PR 已合并”解释为“已经发布给受影响用户”。

一次分诊至少回答：报告者想解决什么、属于哪种问题、目前确定了什么、缺什么、下一步为何这样做、需要谁决定。所有类型共享这个入口，但不共享一条强制流水线。

## 2. 分类体系：把容易混用的概念分开

| 维度 | 建议值或含义 | 产品规则 |
|---|---|---|
| 对象 | Issue / PR | 来自 GitHub；不因 AI 分类改变 |
| 主类型 | Bug、Feature、Docs、Question、Maintenance、待判断 | 一个主类型；信息不足可待判断，不硬归为维护 |
| 子类型 | 按主类型细分，见后文 | 可选，多数用户不必手工填写 |
| 影响属性 | 安全、性能、兼容性、可访问性、数据完整性等 | 可跨类型，影响处理方式，不另造互斥主类型 |
| 严重度 | 影响程度、范围、是否有替代方案 | 对 Bug 等有意义；不强迫为咨询设置严重度 |
| 优先级 | P0–P3 建议及理由，允许未定 | 排期建议，维护者可改；不由类型直接推导 |
| 阶段 | 分诊、调查、方案、实施、验证、PR 跟踪等 | 说明正在做什么 |
| 等待 | 等报告者、维护者、环境、权限、外部依赖 | 独立于阶段，附解除条件 |
| 决定 | 未决定、接受、暂缓、不接受 | 说明维护者取舍；接受不等于马上实施 |
| 结论 | 已交付、已解答、重复、无法复现、过时、不在范围、撤回等 | 必须有理由；不等于已经关闭远端 Issue |
| 远端状态 | open / closed，以及可获取的关闭原因 | 同步事实，不由本地任务结束覆盖 |
| 标签 | 仓库已有 GitHub labels | 类型映射到标签是可选动作，不强制创建新标签 |

默认允许自动生成本地建议，类型有歧义时展示依据和备选。人工改类型后保留历史，重新检查新类型所需材料，不删除原有调查。

### 分类判据与边界

- **Bug**：现有、已承诺的行为不符合预期。崩溃、回归、错误结果、兼容性失效、性能退化可作为子类型。
- **Feature**：希望增加或改变产品能力。新增能力、体验改善、新集成、扩展现有功能可作为子类型。
- **Docs**：主要交付物是文档或示例。错误内容、缺失说明、失效链接、不可运行示例、翻译可作为子类型。
- **Question**：希望获得使用、配置、集成或原理说明；尚无足够依据认定缺陷。
- **Maintenance**：主要目标是保持工程健康。依赖更新、重构、测试补充、CI/构建、清理和开发工具可作为子类型。
- **待判断**：报告目的不清或存在多个合理解释；只补充影响分流的最小信息。

“性能问题”若是已有性能承诺失效，属于 Bug；新性能目标可能属于 Feature；无产品行为变化的工程优化可能属于 Maintenance。“升级依赖”若用于修复已确认缺陷，主事项仍可为 Bug，依赖升级是实现手段。

一个 Issue 同时包含多个独立目标时，保留一个主事项并提出拆分建议。维护者确认后才创建子事项；每个子事项有自己的验收条件，原事项保留聚合进度。不能因为文中提到了文档，就把所有功能需求拆成文档任务。

## 3. 共用入口：分诊的具体职责

### 3.1 输入

标题、正文、可获取的讨论、模板字段、既有标签、关联 PR、近期相关事项以及缓存的仓库摘要。仓库摘要注明版本和覆盖范围，包括用途、模块、贡献规范、测试入口、支持版本与问题报告约定。

Issue 中引用的命令和链接是待判断的资料，不是执行指令。轻量分诊不运行报告者提供的脚本，不安装依赖，不承诺已经阅读完整源码。

### 3.2 输出

1. 主类型、子类型、分类依据；若存在歧义则列出备选。
2. 一句话问题陈述：谁在什么情况下，希望得到什么结果。
3. 已知事实、未验证陈述、关键信息缺口；每项附来源。
4. 影响范围与优先级建议，依据不足时明确未定。
5. 疑似重复与现有 PR 关系，说明相同点和未确认之处。
6. 类型对应的下一动作、动作理由、当前阻塞和需要决策的人。
7. 如确实需要对外回复，生成一份可编辑草稿，而非自动发布。

分类后进入类型专属流程。分诊不得作出根因已证实、需求已接受、补丁有效或已解决等越级结论。

### 3.3 信息追问

只问会改变下一步的信息。区分“阻塞项”和“有帮助但可稍后补充”；先利用已有讨论和仓库资料。一次聚合追问，显示已问、已答、仍缺什么。等待期间不重复执行同一任务；新回复只触发本地重新评估建议，不默认再次发评论。

## 4. Bug：从报告到可证实的修复

### 必要信息与分流

信息卡包括预期行为、实际行为、版本/提交、环境、触发步骤或输入、日志/错误、频率、影响和临时绕行方式。并非每个字段必填：稳定崩溃栈可能足以开始调查，不应机械要求截图。

- 有现成修复 PR：跟踪该 PR，先核对是否覆盖本报告。
- 报告不够定位：聚合追问，等待报告者。
- 报告清楚且修复局部：接受后在一次实施任务内完成复现、修复、验证。
- 原因不明、影响较大或多个假设：独立调查；不能先猜修复再补证据。
- 潜在敏感安全问题：交维护者决定披露方式，公开草稿不展开敏感细节；严重度仍需证据。

| 阶段 | Agent 工作 | 交付物与退出条件 | 页面主动作 |
|---|---|---|---|
| 补充信息 | 检查缺口、组织最小追问 | 足以选择调查环境，或明确无法继续的原因 | 编辑追问 / 标记已补充 |
| 调查复现 | 在固定版本验证异常，区分事实与假设 | 复现命令、输入、实际结果、预期结果；不能复现时列覆盖范围 | 接受调查 / 补充环境 |
| 修复方案 | 确认修复边界、兼容影响和测试策略 | 根因证据或明确的假设性缓解方案，验收条件 | 确认修复范围 |
| 实施 | 修改代码并补回归覆盖 | 补丁与检查记录；解释未覆盖条件 | 验证修复 |
| 验证 | 核对原始场景、相邻行为和环境限制 | 修复前后结果；无法执行时保持未验证 | 审查变更 |
| PR 与交付跟踪 | 关联原始报告，复核新提交 | PR 状态、合并版本、发布状态分开记录 | 查看 PR / 核对交付 |

“无法复现”不是“没有 Bug”。允许转入等待环境、保留观察或建议关闭；关闭建议必须说明尝试的版本与条件。若发现行为符合设计，则建议转 Question 或 Feature，维护者确认后转换。

验收重点：原始异常消失、已有正常行为不回退、报告的关键环境被覆盖或明确未覆盖。对间歇性问题记录重复次数和仍存在的不确定性；禁止仅凭一次成功宣称消除。

## 5. Feature：从需求取舍到功能交付

### 必要信息与分流

需求卡包括目标用户、实际场景、当前困难、现有替代办法、期望收益、范围/非目标、约束、验收示例。用户提出的技术方案作为候选，不直接视为必须采用的实现。

流程：需求澄清 → 价值与范围决策 → 方案 → 实施 → 验证 → PR → 交付跟踪。

| 阶段 | Agent 工作 | 维护者决定 | 必须交付 |
|---|---|---|---|
| 澄清 | 把方案描述还原为使用问题，检查已有能力是否满足 | 是否确有新增需求 | 场景、目标、替代方案、缺口 |
| 取舍 | 对照仓库定位、相关讨论、维护成本提出建议 | 接受 / 暂缓 / 不接受，及理由 | 决策记录；暂缓附重新考虑条件 |
| 方案 | 调查扩展点，比较必要的实现选择 | API、交互、数据或兼容性取舍 | 范围、非目标、设计、迁移要求、验收条件 |
| 实施 | 按已接受范围修改代码、测试和必要文档 | 范围变化是否接受 | 补丁、行为说明、验证记录 |
| 验证 | 检查正向流程、边界、权限/错误处理和兼容性 | 未覆盖项是否可接受 | 按验收条目逐项给证据 |

接受与启动是两个动作：维护者可以接受进待办而不消耗模型运行成本。小功能可将范围确认与启动合并为一次操作；涉及公开 API、持久化结构或较大交互变化时先确认方案。调查不等于承诺开发。

Feature 不要求“旧版失败的 Bug 测试”；需要证明新行为满足验收且不破坏已有行为。不得仅凭“代码编译通过”判断需求交付。

## 6. Docs：面向读者任务的文档流程

信息卡：页面/路径、适用版本、目标读者、错误或缺失内容、正确行为的来源。子类型为错漏、教程、API 说明、示例、链接、翻译。

流程：确认问题 → 编辑计划（较大文档）或直接修改（小错漏）→ 文档验证 → PR。

- 错误说明：对照实际接口、源码或已验证行为，避免用另一个 AI 猜测替换原文。
- 缺失教程：确定读者起点、预期完成任务和环境前提，再编写步骤。
- 示例代码：尽可能执行；未执行必须标注环境或依赖限制。
- 翻译：保留术语、代码、锚点和语义，优先复用仓库术语规范。
- 链接/格式：运行仓库已有文档构建或检查；没有检查器时记录实际检查方式。

验收：内容对应正确版本，步骤可跟随，引用可追溯，适用的构建/链接/示例检查有记录。文档错误实际源于代码缺陷时可转 Bug，原文档诉求作为关联目标保留。

## 7. Question：先把问题回答清楚

信息卡：想完成的任务、使用版本、已尝试步骤、具体卡点。流程：理解问题 → 检索与必要验证 → 答案草稿 → 维护者确认发布 → 等待反馈 / 已解答。

答疑 Agent 负责引用适用版本的仓库文档、源码位置或实际验证，提供最短可操作步骤，注明前提和不确定之处。轻量分诊可以生成基于现有资料的短答草稿；复杂问题进入独立答疑任务，不能让分诊暗中承担完整调查。

- “生成答案”“发布答案”“用户确认有效”“关闭 Issue”是不同事件。
- 未回复不自动标为用户确认解决；可由维护者判定已充分回答并说明依据。
- 发现产品缺陷：保留尝试记录，建议转 Bug。
- 现有能力不足：建议转 Feature，并进入需求取舍。
- 高频问题：提出文档任务建议；用户的问题可先答完，不必等文档 PR。

主动作是“生成答复 / 编辑并发布答复 / 转为 Bug 或 Feature”，不默认显示“实施修复”。不需要 PR 的事项也能完成有效闭环。

## 8. Maintenance：目标不同，验证方式也不同

| 子类型 | 开始前要明确 | 核心验证 | 禁止的简化 |
|---|---|---|---|
| 依赖更新 | 更新目的、目标版本、兼容性、锁文件及许可影响 | 相关测试、构建、迁移步骤；安全修复需确认适用条件 | 只改版本号就称升级成功 |
| 重构/清理 | 必须保持的外部行为、边界、迁移要求 | 行为等价证据、接口/测试检查 | 借重构扩大产品范围 |
| 测试补充 | 要覆盖的风险与现有缺口 | 测试能识别目标错误，运行稳定 | 只增加行数或镜像实现 |
| CI/构建 | 失败运行、提交、环境、历史基线 | 区分变更回归、既有失败、偶发失败、环境问题 | 删除检查或放宽断言冒充修复 |
| 开发工具 | 目标开发任务、现有步骤、支持平台 | 在声明环境中执行代表性流程 | 只提供不可运行脚本 |

流程：明确工程目标 → 必要诊断 → 范围确认 → 实施 → 子类型验证 → PR。紧急 CI 回归可以归 Bug；维护类型不能成为不明问题的垃圾桶。

## 9. 共同异常、转换与收尾

- **重复**：给候选、相同点、差异和证据；可仅确认同一需求而不声称相同根因。维护者决定关联/关闭，对外评论另确认。
- **已有实现或修复**：核对适用版本，提供升级/使用说明；远端关闭和用户问题得到解决分别记录。
- **暂缓**：保存原因、依赖和恢复条件，不持续消耗 Agent；无必要不建立自动提醒。
- **类型转换**：保留全部历史和关联，作废不适用的验收条件，提示需新增哪些材料。
- **内容改变**：重新评估受影响的判断；证据保留为历史，不全部删除或全部当作有效。
- **重新打开**：保留旧交付记录，以新发生的条件判断是同一问题回归还是新问题。
- **拆分与阻塞**：允许一个事项关联多个 PR，一个 PR 支持多个事项。每个验收条目标明由谁实现，不能因任意一个 PR 合并就完成所有事项。
- **关闭建议**：说明结论、依据、未完成项；用户明确执行远端关闭才改变 GitHub。默认不自动关闭、合并或发言。

## 10. Agent 分工与交接契约

不为每个步骤新建一个自治 Agent。以共享执行器、类型专属指引和结构化产物组合，减少重复读仓库和上下文漂移。

| 职责 | 输入 | 输出 | 不负责 |
|---|---|---|---|
| 分诊 | 元数据、讨论、缓存仓库摘要 | 类型、缺口、关系、建议路径 | 深入复现、需求承诺、仓库修改 |
| 调查/诊断 | 明确疑问、版本、已有证据 | 事实、假设、实验、边界、阻塞 | 未授权扩大修改范围 |
| 需求/方案 | 用户场景、仓库约束、必要调查 | 范围、非目标、选择、验收条件 | 替维护者决定是否接受需求 |
| 答疑 | 问题、版本、文档与证据 | 有来源的答复、限制、转换建议 | 默认创建补丁 |
| 实施 | 已接受范围、验收条件、有效证据 | 补丁、变更说明、自检结果 | 自行宣称独立审查通过 |
| 验证 | 固定补丁版本、验收条件 | 每项结果及命令/输出/未运行理由 | 顺手改代码使检查通过 |
| 审查 | 当前 diff、关联目标、验证证据 | 有依据的发现、覆盖与遗漏 | 代替需求验收或远端人工批准 |
| 跟踪 | GitHub 状态、关联关系、发布事实 | 交付进度、需关注变化 | 从任务成功推测已经发布 |

每次交接带：事项与仓库标识、类型及其人工修正、源版本、目标/非目标、已接受决策、验收条目、证据引用、未决问题、相关补丁/PR、权限与工作区边界。资料正文属于不可信内容，不能覆盖执行器权限。

提示词采用共用约束 + 类型指引 + 阶段契约；仓库约定作为可追溯上下文注入，不要求用户编写提示词。不同仓库可自动识别约定，但冲突时展示来源并由维护者决定。

## 11. 界面与操作细节

### 队列

顶部以“需要我决定、待补充、可开始、运行中、待审查、跟踪中”为工作视角；类型筛选独立存在。列表显示主类型、简短问题、当前阶段、阻塞对象、优先级依据入口、最新有效结论与关联 PR。运行失败独立显示，不把失败解释为产品流程的结论。

批量操作先预览每项动作。允许批量分诊和统一接受明确分类；需求取舍、关闭、发言和发布变更不能通过一个模糊的“全部处理”按钮混在一起。不同类型使用各自下一步，不强制对一批 Issue 全部启动修复。

### 详情

1. 顶部：类型（可修正）、阶段、远端状态、一个推荐主动作及原因。
2. **目标与信息卡**：随类型变化；显示“来自报告者 / Agent 推断 / 维护者确认”。
3. **处理计划**：已完成、当前、可选下一步；小任务可跳过独立方案任务，必要验收不能跳过。
4. **证据与验收**：逐条显示通过、失败、未运行、无法判断，能打开来源。
5. **讨论与决策**：聚合追问、答复草稿、范围取舍与待回答问题。
6. **变更与关联**：补丁、PR、依赖事项、交付版本。
7. **执行记录**：会话、成本/耗时（仅已获取数据）、失败恢复；不占据默认主视图。

主动作来自类型、阶段、决策和证据状态的确定性规则，模型只提供建议和理由。按钮禁用必须解释缺什么；“其他操作”允许专家选择替代路径。误分类能就地纠正，不需要重新导入仓库。

### 易用性与仓库适配

首次接入只选择仓库并确认身份权限，沿用 Harness 模型。读取已有模板、贡献指南、标签与检查配置建立建议映射；用户无需先配一套工作流。映射来源和最后更新时间可查看；不存在规范时使用保守默认值，不伪造仓库约定。

多仓库共享产品流程，但分别保存标签映射、上下文、决定、队列、预算和权限。相同标题不能跨仓库直接判重复；跨仓库依赖作为显式关联。

## 12. 数据契约与状态规则（建议，尚未实现）

建议以版本化结构取代随意的阶段字符串，并保留兼容读取：

- `classification`：主类型（含 unknown）、子类型、影响属性、依据、来源、人工覆盖。
- `typeDetails`：按类型的判别联合结构，避免一个含几十个可选字段的大对象。
- `decision`：接受/暂缓/不接受、理由、操作者、时间、适用的范围版本。
- `phase` + `waiting`：分别记录工作阶段和等待对象/解除条件。
- `acceptanceCriteria[]`：稳定 ID、要求、适用版本、验证方式、结果、证据引用。
- `questions[]`：稳定 ID、问题、是否阻塞、来源、是否已发布、回答及解决状态。
- `relationships[]`：重复/阻塞/实现/相关，目标标识、依据、人工确认。
- `resolution`：结论与依据；远端关闭仍来自独立同步字段。

关键状态约束：

1. Feature 未接受时可澄清和调查，不能自动开始实施；接受但未启动仍在待办。
2. Question 发布答复后进入等待反馈或维护者判定，不能直接变为“报告者已确认”。
3. 没有可用补丁不能进入发布代码；有补丁但未验证必须显示未验证。
4. 新提交使旧版本测试与审查不再作为当前通过依据；历史资料可作为线索。
5. 暂缓/等待不会自动重排相同任务；解除条件满足后给出下一步或按已明确配置的策略推进。
6. 只更新本地分类、决策和阶段不产生 GitHub 写入；写入动作有明确预览、授权和回执。
7. GitHub 已关闭但本地仍有未决验收时，两种状态同时显示，并提示维护者核对。
8. 状态变更与对应事件原子保存；任务去重、失败重试和发布幂等不因新增类型失效。

## 13. 实现拆解与验收场景

### 第一批：分类到正确动作

补充 unknown、子类型和人工修正；类型信息卡；确定性的下一动作规则；Feature 接受与启动分离；Question 专属答疑；类型专属 Skill 和结构化产物；历史数据兼容迁移。

验收：提问不会直接派发修复；未接受 Feature 不自动写代码；清晰文档错字能走短路径；人工修正刷新建议且不丢历史；旧任务仍可打开。

### 第二批：证据驱动的阶段交接

实现逐项验收、聚合追问、回答归并、范围决策、类型转换、暂缓/恢复和新版本失效规则。

验收：已回答的问题不重复追问；缺环境时显示等待而非一直运行；Feature 需求变化后旧验收不会继续显示全部通过；Bug 未复现不能写已证实根因；模型输出损坏保留原始证据并可恢复。

### 第三批：Issue 与 PR 的完整关系

多事项/多 PR 关联、现有 PR 复用、关闭建议、合并与发布跟踪、批量操作预览、仓库映射与权限异常处理。

验收：关联两个 PR 的需求不会在第一个合并后被整体标为交付；已有修复 PR 不重复创建；没有写权限时可完成分析并清楚说明发布阻塞；重复点击不会重复发评论或建 PR。

### 代表性端到端场景

| 输入 | 预期路径 | 关键断言 |
|---|---|---|
| “新版启动崩溃”，无版本日志 | Bug → 最小追问 → 等回复 → 调查 | 不编造复现，不重复追问 |
| 可稳定复现的局部边界错误 | Bug → 接受并实施 → 验证 → 审查 → PR | 有修复前后证据，PR 创建不等于解决 |
| “希望支持离线导出” | Feature → 澄清 → 维护者取舍 → 方案 → 实施 | 明确格式、范围、错误场景等验收，未接受不实施 |
| “如何配置代理” | Question → 检索 → 答复 → 反馈 | 答案有适用版本，不生成无关补丁 |
| 文档命令实际无法运行 | Docs → 核对行为 → 修改或转 Bug | 转换保留原始任务和验证结果 |
| CI 在当前 PR 失败，主分支也失败 | Maintenance/CI → 诊断 → 决定 | 不直接归咎 PR，不删除检查冒充修复 |
| 需求已存在进行中的 PR | Feature → 关联并核对覆盖 → 跟踪 | 不另开重复实现 |
| 合并后用户报告同场景仍失败 | 重新打开 → 核对环境与版本 → 回归调查 | 保留上次交付事实，不照搬旧通过结论 |

以上为设计验收标准，不是已经通过的测试结果。实现时每批都应验证用户可见流程、状态一致性与真实工具边界；模型效果另用代表性案例评估，不能由界面或单元测试推导。
