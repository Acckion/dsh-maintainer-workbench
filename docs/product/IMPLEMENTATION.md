# 工作流实现与验收记录

日期：2026-09-26。对应本地工作区变更；尚未提交或推送本轮代码。

## 可运行的产品流程

- 首页“需要我处理”跨仓库汇总事项，按事项而非尝试次数计数。仓库队列仍可分别筛选 Issue / PR。
- Issue：快速分诊输出模块、影响、信息缺口、疑似重复和处理去向；可记录接受、等待信息、暂缓，再交接调查、实施、验证和独立审查。代码交接会把来源补丁应用到新工作区，不只传递提示词。
- PR：独立预检，读取固定 head/base、草稿、合并状态、CI check runs、commit status、审查及行内评论。深度任务 fetch GitHub PR head ref（包含 fork），校验与 API SHA 一致后创建工作区。比较基线与执行 SHA 分别传给模型。
- 审查发现逐条记录接受、需要证据、不适用、已解决。下一阶段接收这些处置、历史产物、验收条件与维护者反馈；“已解决”明确为维护者判断。
- 实施、验证、审查使用独立工作区。调查可按宿主权限写临时复现材料；实验差异不得由发布器发布。审查、验证、CI 诊断若修改代码，则拒绝作为完成产物交付。
- 发布沿用明确预览：回复、标签、草稿 PR、原 PR 分支更新、已采纳发现的 GitHub Review COMMENT。原 PR 更新正常 push、不强推；fork 保留补丁导出路径。创建 PR 后记录关联链接，不把事项标为已解决。
- 分析任务完成后进入 completed；修改与审查仍进入待审。远端发布必须确认，远端合并/关闭是独立事实。历史旧版 Analysis 继续可读，新的八类任务保存 schemaVersion=1 阶段产物，并保留兼容投影供导出/发布使用。
- 分诊与预检禁止任意工具：不挂载 coding preset，宿主 tools.restrict + guard 双重约束，不创建代码 worktree，仅使用缓存摘要与受限元数据；时间预算最多 120 秒，输出预算沿用仓库/全局设置（默认 6000 token，包含部分模型的推理开销），并要求简短报告。实际测试发现 2400 token 对继承 High 推理的模型可能不足，因此不强制使用该低上限。
- 模型继续继承 Harness 默认 provider/model/reasoning；代码任务保留宿主 preset 和权限机制。审批等待会显示在任务中。
- 结果格式失败自动启动一次无工具整理会话，仅整理已记录输出。再次失败后手动重试仍优先复用原始输出及工作区，不重新实施。缺失事实必须标为未知，不补造测试结论。
- Issue 轻量分诊不因无关仓库提交过期；代码任务仍绑定代码版本。PR 发布前重新核对 head/base；队列执行前核对输入。失效产物显示过期，旧反馈保留。
- 调度按仓库轮转、同事项串行；发布对同目标分支互斥。每仓库可以设置自动分诊、轮询周期、时间和输出预算，默认继承全局值。批量分类分别处理 Issue/PR，并报告逐项失败。

## 已验证

1. `npm run check`：类型检查、38 项自动化测试、完整构建。测试包括 100 条轻量任务无工作区、公平调度、代码版本过期、反馈交接、补丁传入新验证/审查工作区、PR head 竞态、逐条发现、审查发布丢失响应后去重、原分支实际本地 push（本地 bare remote）。
2. `npm run test:native`：隔离 DSH_HOME 与临时仓库，使用确定性本地模型服务，但调用真实 Harness agent、权限机制、shell、Git 工作区和回归命令。观察 BASELINE_FAILED_AS_EXPECTED / REGRESSION_PASSED，产出真实补丁；轻量任务无 shell 工具、无 worktree。此测试不代表真实模型质量评估。
3. 真实 Harness 默认模型 `deepseek-official/deepseek-flash` 已完成私有仓库 PR 的元数据预检，保存阶段产物，未创建代码工作区。check-runs 读取返回 403 时显示未知和权限缺口，没有计为通过。首轮发现执行 SHA 与比较 base 字段命名易混淆，已分开字段并修订预检技能；修复后再次实测完成，正确输出 readiness=review，不再把缺少本地测试或正常的 head/base 差异视为阻塞，同时仍保留 CI 权限不足、不能据此批准合并的限制。
4. 浏览器验证在原端口 4318 执行，使用已有真实仓库；测试夹具不注入用户工作区。远端发布未用于真实仓库写入验收，相关验证使用本地 Git 和模拟 GitHub API。

## 范围边界

- 尚不自动合并、自动关闭、指派负责人或发布 release；这些在设计中已列为后续。合并入口由 GitHub 完成。
- Review 以 COMMENT 汇总已采纳发现，不代替人工 APPROVE / REQUEST_CHANGES；可以读取行内评论，但没有 GitHub review-thread resolve/unresolve 操作。
- CI 支持读取状态与 check 输出并诊断；不会自动下载任意 CI 提供商的完整日志/归档。权限不足、日志缺失时必须给出无法验证，不能保证所有平台的 CI 均可诊断。
- CI/审查/评论目前最多各 100 条，diff 最多 100 个文件，讨论最多 30 条；覆盖限制随结果展示。分支保护、merge queue 等规则未完整求值，不提供自动合并许可。
- 测试结论仍来自 Agent 报告，真实工具事件另外作为证据保存；不把模型 JSON 中的 passed 独立当作可信执行证书。任意仓库的依赖、平台和许可问题仍可能阻塞执行，宿主审批仍需维护者处理。
- 同一模型下的采纳率、审查误报率、耗时/成本对照实验尚未完成，不能据此宣称智能质量优于其他产品。


## 2026-10-02：恢复路径与证据完整性修复

本轮基于远端 `853bc5a75cc2823e407d8a0a6123cabca85d3985` 的逐文件 SHA 校验快照，在独立本地分支开发。未执行远端推送或真实 GitHub 发布。

- 恢复只接受明确的产物格式失败，不再把工具失败、取消、越界修改等任意失败当成“只整理输出”。
- 格式恢复保存固定提交和补丁 SHA-256；整理前、整理完成后及再次格式失败时均验证工作区和 HEAD。PR head/base 变化、整理期间并发修改、取消期间的异步检查都不能把旧产物重新变成可交付结果。真正的格式失败仍复用原工作区，不重复实施。
- 无本地执行能力的结果，先在阶段产物中把测试状态强制归为 `not_run`，再生成兼容投影。持久化、JSON 导出和下一阶段交接不会保留模型臆报的 passed/failed 状态。原始模型输出仍作为待核查原文保存。
- 补丁包含可应用的 Git binary patch，并保留末尾块分隔符。二进制新增、修改、删除和混合文本变更均可交接到独立验证/审查工作区及导出后应用。纯文本补丁保持旧表示，避免已保存任务被无意义地判为变更。
- 测试入口改为 `node --import tsx --test`，避免 tsx CLI 创建额外 IPC 管道；仍运行原有 TypeScript 测试。

这些修复证明工作流的正确性与证据边界，不证明真实模型修复成功率、采纳率或成本优于其他产品。
