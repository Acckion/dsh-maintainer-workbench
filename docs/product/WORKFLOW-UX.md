# 按事项类型展示处理阶段的 UI/UX 设计

状态：已实现阶段导航与只读投影；更细的分类维度为后续扩展。2026-10-09。分支 `feat/workflow-timeline`，起点 `2ba01e3`（最新 master）。

## 目标与范围

保留既有 Issue/PR 状态机、阶段执行权限、审批、交接、发布和 worktree 隔离规则。在界面增加可点击的横向阶段导航，回答：现在处于哪里、之前发生过什么、下一步为什么可以或不可以执行。

导航显示已发生的处理阶段、当前阶段和可能的后续阶段；它不是按百分比增长的进度条。PR 可以等待作者修订，Issue 可以等待信息，验证可以退回修改，事项也可以暂缓。界面不得把这些过程表示成必然一次完成的流水线。

点击阶段只切换查看内容；启动任务、继续任务、批准或发布必须点击独立且具体的操作按钮。查看历史不重新运行 Agent，不回滚状态，不使用历史审批替代当前版本审批。

## 详情页布局

1. 标题与事实行：Issue/PR 编号、作者、远端状态（含 Draft）、当前本地处理状态、同步时间。
2. 阶段导航：位于事实行下方，横线连接阶段节点；阶段名、状态和必要的次数直接可见。
3. 当前阶段的面板展示下一步条件与独立操作按钮；查看历史或下一步预览时，显示一行实际当前进度与“返回当前阶段”。不重复展示整个当前结论。
4. 下方只显示选中阶段的内容：来源版本可展开；多次尝试可切换；结论与证据、执行记录为两个视图。阶段面板不拼接其他阶段的摘要。节点选中背景在圆点上方保留 14px 留白。
5. 右侧 GitHub 原始资料：保留 Summary / Activity / Diff，支持与阶段证据并排核对。手机通过现有选择入口切换。

移除独立 Overview / “处理概览”入口；旧概览选择自动返回当前阶段。跨阶段验证与交付证据在维护者确认、交付与跟踪阶段按需展开。原 Plan / Work / Review 不再与阶段导航形成两套平行的顶层页签：计划编辑、执行记录和审查组件分别放入相应阶段。保留旧深链接和已有草稿；旧入口映射到对应节点，不产生执行。

右上角不再统一显示“调查并修复”。主要操作随当前状态变化，例如“开始预检”“开始审查”“补足审查证据”“准备仓库环境”“根据补充信息继续”“检查审查结论”。次要合法操作放在“更多操作”，同时显示阻塞原因。

## 按类别展示路径

### Issue

| 类别 | 默认展示路径 | 当前阶段重点内容 |
| --- | --- | --- |
| 尚未分类 | 分诊 → 后续路径待确定 | 信息完整性、重复项、分类依据 |
| Bug | 分诊 → 复现与定位 → 范围确认 → 修复 → 验证 → 补丁审查 → 交付与跟踪 | 复现条件、预期/实际行为、根因与回归证据 |
| 功能建议 | 分诊 → 需求澄清 → 范围确认 → 实现 → 验证 → 补丁审查 → 交付与跟踪 | 用户目标、边界、不包含项、兼容性、验收条件 |
| 文档 | 分诊 → 文档核对 → 范围确认 → 更新 → 验证 → 补丁审查 → 交付与跟踪 | 文档与源码差异、示例和链接、对应功能版本 |
| 提问 | 分诊 → 查证与答复 → 答复审核 → 发布与跟踪 | 引用依据、答复草稿、尚未确认内容；不预告代码修改 |
| 维护 | 分诊 → 影响调查 → 范围确认 → 实施 → 验证 → 补丁审查 → 交付与跟踪 | 维护目标、受影响模块、行为变化与风险 |

这是展示模板，不是新执行条件。已确认范围的事项可以跳过重复调查；信息不足在所属阶段显示等待，不自动添加一个必走的追问阶段。实际出现的阶段始终保留，即使分类后来变化。

### PR

PR 使用两个独立维度：变更意图（缺陷修复/功能/文档/测试/重构/构建依赖/混合/待确定）和影响范围（例如 Gateway、插件生命周期、测试夹具）。不能用一个 maintenance 标签代替两者。

| 类别 | 默认路径 | 审查重点 |
| --- | --- | --- |
| 缺陷修复 | 预检 → 缺陷审查 → 维护者确认 → 交付与跟踪 | 根因、复现、修复范围、回归测试 |
| 新功能 | 预检 → 功能审查 → 维护者确认 → 交付与跟踪 | 需求、兼容性、验收条件和迁移 |
| 文档 | 预检 → 文档审查 → 维护者确认 → 交付与跟踪 | 内容真实性、示例、链接与源码一致性 |
| 测试/夹具 | 预检 → 测试审查 → 维护者确认 → 交付与跟踪 | 断言是否削弱、时序/隔离、失败反证、重复运行与联动证据 |
| 重构/维护 | 预检 → 变更审查 → 维护者确认 → 交付与跟踪 | 行为保持、模块边界、依赖与构建影响 |
| CI/构建/依赖 | 预检 → 构建审查 → 维护者确认 → 交付与跟踪 | 运行矩阵、供应版本、安装与发布行为 |

审查发现证据不足时显示“补充调查”；发现需要修订且维护者选择 Agent 时才展示“修订 → 验证 → 复审”。选择作者修订则显示“等待作者修订”，新提交触发重新评估。Draft PR 可被审查，但不能因为执行完成或未发现问题而显示可以交付；真实操作条件沿用服务端校验。

分类先使用现有分类结果、明确文件差异与仓库资料；标题只能提供辅助线索，GitHub 标签不能单独证明类别。路径/文件用于影响范围，缺失完整差异时在阶段证据中如实说明覆盖范围。混合变更保留多个关注点；未知时用通用审查，不能为了选择模板额外调用模型或阻塞现有功能。

## 阶段节点与交互

节点的业务阶段、执行状态、证据结果和选中状态分开表示。

| 节点状态 | 表现 | 点击后的内容 |
| --- | --- | --- |
| 有已保存结果 | 实心节点/结果图标，明确结果文本 | 阶段摘要、证据、当时决定及所有尝试 |
| 排队/运行 | 时钟/运行图标，文字“排队中/执行中” | 当前动作、会话/工具记录、耗时、停止操作 |
| 等待 | 等待图标及文字，例如“等待范围确认” | 谁需要做什么、等待原因、合法继续入口 |
| 阻塞/失败 | 警示图标和具体类型 | 网络/环境、执行失败、验证失败或证据不足及对应恢复办法 |
| 已过期 | 过期标记及来源提交 | 只读旧证据，说明哪项输入已变化 |
| 未开始/可能下一步 | 灰色空心点，“待开始”或“可能下一步” | 阶段目的、进入条件；只有满足条件才提供独立启动按钮 |

实心节点或绿色不能单独表示“可以合并”。验证成功、阶段执行结束、无阻断发现、维护者批准和远端合并必须使用不同的结果文字。颜色之外保留图标和文字。

进入详情默认选择实际当前阶段。查看历史时轮询不抢回当前阶段；出现新结果显示“当前阶段有更新”。未主动选择历史的用户可以随当前阶段前进。未来节点可点击查看说明，但点击本身绝不调用派发接口。

初始最多显示 5–7 个主要节点，较长路径可横向滚动。桌面展示完整标签；手机保持可横向滚动、最小 44px 点击区域和“当前：阶段名 · 状态”提示。支持键盘切换节点、可见焦点、aria-current、明暗主题和减少动态效果设置。轮询更新不反复宣读完整日志。

## 历史、循环与版本

导航表示业务阶段；下方的阶段活动记录表示真实时间顺序。不能用模板排序伪造执行先后。

- 同一阶段重试显示“审查 · 第 2 次”，在节点下选择尝试，保留第一次失败和恢复决定。默认显示当前适用尝试；用户选择旧尝试后不被新结果覆盖。
- 修订、验证失败、复审等循环用“修订轮次”分组。阶段活动按真实发生顺序展示“首次审查 → 调查 → 复审”，以免把后来的调查错误展示成发生于首次审查之前。
- 新 PR head 或 Issue 信息变化时，旧产物标记来源版本与适用性。旧结果可查看，不能支撑新版本的批准或发布。
- 不同处理周期独立，提供“周期 1（已结束）/周期 2（当前）”切换。历史周期没有当前执行操作。
- 迟到的旧运行结果只更新所属历史阶段；不能变成当前节点。现有 sourceFingerprint、caseId 和运行来源约束继续生效。
- 不按每条工具日志建立节点。GitHub 活动、等待和人工决定进入对应阶段的活动记录；低层事件历史保留为可展开的技术详情。
- 如果没有足够数据证明修订轮次，只按同阶段尝试分组，显示真实时间记录，不猜测因果链。

## 当前阶段的内容结构

每个阶段统一显示“目标 → 当前状态 → 结果/证据 → 下一步”，并按类别调整中间部分。运行中展示正在做什么；执行结束展示实际产物；停止或失败保留已保存内容。

证据与缺口分四类：

1. 用户/作者信息不足：明确问题、期望回复者和输入表单；真正需要回答时才进入对应输入等待。
2. Agent 取证不足：缺源码、截断日志或未读完差异，提供“补足审查证据”；不伪装成用户需要回答的问题。
3. 环境不足：克隆、依赖、权限或运行条件，提供现有环境恢复/宿主审批入口。
4. 外部资格条件不足：CI、作者新提交、来源 PR 落地或重复验证，说明需要的证据与责任方。没有对应机器可验证状态时显示审查限制，不擅自创建新的后台等待或自动轮询规则。

下一步始终包含动作、理由和条件，例如“下一步：验证改动。将检查当前补丁的验收条件”，或“下一步：复审。等待作者提交新版本”。没有可执行后续时显示“等待维护者检查审查结论”，不能留一个没有解释的灰点。

历史阶段顶部显示“正在查看历史 · 第 1 次审查 · 提交 abc123”。原始执行记录、审查发现、命令结果和 GitHub 来源均可访问。最新结论与当时结论分开，不能用当前 Issue.analysis 覆盖历史任务的 artifact/result。

## 示例：PR #166828

标题事实行保留 PR 编号与 Draft；进度条上方不额外展示分类、模块路径、初步判断标签或分类依据。

阶段导航示例：

```text
[✓ 预检] ── [! 测试审查] ── [● 补充调查：待开始] ── [○ 复审：可能下一步] ── [○ 维护者确认]
```

“待开始”只在服务端确实允许启动调查时显示；否则当前焦点停留在审查，并注明阻塞原因。Agent 已在调查则显示执行中；产物产生后根据事实重新投影。

当前阶段提示：审查证据不足；未确认补丁引入的阻断问题。需要重新读取截断源码并核对已有分片运行失败的反证。来源资格验证/落地条件仍未满足，保持 Draft。

主操作“补足审查证据”，次要操作“查看执行记录/查看 PR 证据”。用户点击前面的预检节点能查看当时风险判断；点击审查节点能查看覆盖范围、缺口和依据；点击复审灰点能查看“调查结果保存且版本仍有效后可再次审查”的条件。

调查结束不会默认显示“待修复”。只有明确需要改动并完成相应维护者决定后，才展示修订路径。外部资格失败也不能自动归因于此 PR。

## 数据与模块设计

不新增持久化的 progress/百分比/第二套状态机。新增只读投影，由处理周期、Job、阶段产物、人工决定、等待、发布回执和远端事实生成。模板只负责展示标题、分组和关注点，不能决定操作是否允许。

- `domain/timeline.ts`：展示模型类型。
- `application/timeline.ts`：在持久化读视图中读取周期、运行、事件，校验版本与周期归属。
- `workflow/timeline.ts`：纯投影，生成稳定的阶段节点、尝试与当前事实；服务端与客户端降级读取共用，无执行与 Node 依赖。
- `workflow/presentation.ts`：类型与关注点模板、运行/结果到显示状态的纯映射；未知版本退回通用展示，不替代 engine/actions。
- `client/WorkflowTimeline.tsx`：节点与横向导航、键盘与窄屏交互。
- `client/StagePanel.tsx`：选择阶段/尝试并复用计划、执行、审查、输入和发布组件。
- `client/WorkflowDetail.tsx`：读取投影、保存选择、轮询与周期切换竞态防护。
- `client/StageResult.tsx`：仅展示所选运行的产物、发现、测试记录与证据链接。
- `client/NextAction.tsx`：历史/预览时的简短当前进度提示。当前阶段的下一步与操作放在 `StagePanel` 内。
- `client/ProcessingHistory.tsx`：保留详细事件和周期追溯，移到阶段活动的展开区域。

只读 `GET /processing/timeline?issueId=...&caseId=...` 返回：caseId/version、profile（类型/范围/依据/判断完整性）、currentNodeId、nodes、活动摘要和与当前 version 对齐的 actions。节点含稳定 ID、stage、状态、attemptIds、结果标签、等待信息、条件后续和事实发生时间；来源版本保存在对应 Job 中。

未来节点没有伪造 runId/完成时间/结果。阶段 ID 不使用数组下标；补足分类或增加结果不应让历史选中项跳到另一个阶段。混合关注点不复制同一任务。

读取响应在同一持久化读视图生成，动作携带 expectedVersion；轮询以 caseId/version 更新。前端增加 request generation，切换事项/周期后丢弃旧响应，派发/审批继续调用原接口及校验。日志与原文按需加载，不将完整工具输出加入频繁轮询。

现有缺失时间、caseId、分类依据等历史记录显示“历史记录信息有限”。不能为填满导航补造阶段、证据、完成记录或决定。

## 实施顺序与验收

1. 先完成纯投影与测试，覆盖类型、等待、重试、版本变化、处理周期、循环和现有合法动作；与当前操作投影逐项核对。
2. 加入阶段导航及内容选择，复用现有阶段组件，映射旧深链接，保留草稿及 GitHub 阅读面板。
3. 按类别组织内容、统一下一步与缺口文案；移除被替代的旧顶层页签/不可达代码，避免形成双入口和双状态。
4. 验证桌面/手机、明暗主题、键盘、刷新及慢轮询竞态。

必须通过的产品场景：

- PR #166828 类似案例能区分已审查、证据不足、Draft 和下一步；不会暗示需要代码修复或可以合并。
- Bug Issue 范围确认前不能越过原有实施限制；Question 路径不会预告无关的代码变更。
- 点击历史和未来节点只读取，Agent/发布调用数不增加；批准或重跑需要明确操作。
- 重试、验证失败后修改和作者新提交均保留旧证据，当前失败不被旧通过遮蔽。
- 原生输入、环境、作者回复、CI 和维护者决定均明确谁需要做什么，恢复规则沿用原状态机。
- 查看历史时轮询不抢焦点；切换事项/周期不会显示旧响应或误向旧事项派发。
- 未执行、未验证、证据缺失和真实通过能区分；历史周期和失效证据不能用于当前交付。
- 没有后台执行、迁移重放、新的自动发布或 worktree 混用；现有功能入口与深链接可达。

## 本次实现的明确边界

- 实际阶段按首次发生顺序展示；同阶段的多次重试/循环通过尝试列表保留，不为每次尝试复制节点。调查期间可追加一个无运行记录的“复审”预告。
- 当前节点以处理周期的 `currentRunId` 为准。输入版本变化使旧产物过期，显示“重新评估”，并提供现有服务端允许的重新执行入口。历史周期与旧尝试隐藏修改/审批/发布按钮。
- 分类依据来自已保存分类与读过的源码路径，仅用于选择阶段标题和关注点；不在进度条上方展示分类、模块路径或依据说明，也不声称已经核对完整 diff；本轮没有增加模型分类调用，也没有实现新的混合分类持久化字段。
- 确认与交付阶段的“关联验证与交付证据”可展开核对同版本、同补丁的完整证据链；默认阶段面板只显示所选运行。PR 的“补足审查证据”只派发调查，不携带自动实施目标；已有确认计划的 Issue 调查明确标为“按计划调查并实施”。
