# 可选复现、定位与范围合并、手动完成阶段

日期：2026-10-11（Asia/Shanghai）
基线：master `8e5c27b`
分支：`feat/manual-workflow-steps`
状态：设计稿；本轮不修改产品代码或大规模重构架构。

## 1. 目标与现状

Bug Issue 默认流程改为：

分诊 → 定位与范围 → 修复 → 验证 → 补丁审查 → 交付与跟踪

复现是“定位与范围”内的可选活动，不再是默认必经节点或继续实施的必要证据。
用户可以不让 Agent 复现，也可以自己提供复现结果。定位允许依据源码、已有日志、
已有测试或维护者补充的信息形成判断；假设与已确认事实必须分开。

现有约束不只来自 UI：`planBlocker` 要求缺陷计划具有 reproduction/expected/actual，
`issueTaskGuidance` 要求建立复现与前后对比证据；`nextGoalStep` 和自动编排都使用这些
检查。实现时必须同步调整，否则改了节点名字仍会阻塞。非空 reproduction 目前只是
复现条件文本，也不能被当成“已经实际复现”的证明。

调查已经使用 investigate Job，范围确认使用 decision/accepted 和 IssuePlan，
自动编排调查完成后已有暂停并确认计划的逻辑。保留这些机制，通过展示聚合形成
一个用户步骤，不合并后台任务类型，不引入通用流程编辑器或新的执行引擎。

第一版只对 Bug Issue 合并上述两个节点。PR 的最终维护者确认不能被合并进补充
调查；其他类别保持原流程，但可以复用手动参与入口。

## 2. “定位与范围”的内容与完成条件

同一个节点分成两种状态：

- 调查中：展示进度；Agent 整理问题位置、判断依据及建议范围。
- 待确认：展示结论和可编辑范围；维护者确认目标、范围和验收条件后完成本节点。

这里有两项不同的完成条件：得到足够的调查材料，以及维护者明确接受实施范围。
Agent 调查结束不等于用户接受范围。主操作由状态决定，不同时铺开所有操作。

```text
定位与范围                         待确认

定位结论
问题可能位于……
依据：源码……；维护者提供的日志……
判断状态：源码判断 / 已有运行证据 / 尚未确认

变更范围     [可编辑]
验收条件     [可编辑]

复现（可选）                 未尝试
[ ] 让 Agent 尝试复现
提供我自己的复现结果

[确认范围并继续]              执行详情  ···
```

这里的“未尝试”“未成功”“环境不满足”都是复现状态，不自动把整个节点标为阻塞。
如果缺失信息确实使目标或范围无法确定，应说明缺哪项决策信息；不把“没复现成功”
本身当成要求用户不断补充信息的理由。

Bug 开始修复仍要求目标、非空范围、至少一项验收条件和维护者接受。expected/actual
作为已知问题描述保留，但空值不再构成机械阻塞。未知内容明确标记，不要求编造。

## 3. 可选复现规则

- 默认不安排主动运行复现；复用已提供的条件、日志与证据。
- 勾选“让 Agent 尝试复现”后，进行一次有边界的尝试；环境不可用、失败或预算耗尽
  时保存结果并继续定位，不自动无限重试或重新请求同一信息。
- 已有任务时间/步骤预算继续生效。复現尝试只占调查预算的一部分，需为源码定位
  留出预算；第一版使用内部限制，不增加复杂设置页面。
- 用户要求“必须复现后继续”时记录为明确的额外完成条件，作为用户要求生效，
  不成为所有 Bug 的默认策略。这个条件未满足时允许用户修改或撤销自己的要求。
- 手动结果可以声明成功复现，但标为“维护者提供”，不会生成 Agent 的工具执行记录。
- 回归测试、补丁验证是否需要运行仍依据验收条件及验证策略，不能因为复现可选就
  把未运行的验证改写成通过。

建议在 IssuePlan 增加可选策略字段 reproductionMode：omit / best_effort / required，
新计划默认 omit；未设置字段的旧计划按默认可选解释，不把非空旧文本解释成 required。
旧 reproduction 字段继续保留原有复现条件，实际复现状态来自执行或手动记录。

## 4. 三种手动参与方式

每个可操作的当前阶段在“更多”中提供：

1. 补充结果：添加自己的观察，Agent 可以继续，不终止当前运行。
2. 我来完成：停止本阶段 Agent 执行，保留已有材料，进入“等待手动结果”。
3. 跳过 Agent 执行：不再安排此阶段的 AI 工作，记录跳过理由和后续条件。

跳过和手动完成不是同一结果。时间线分别显示“已跳过 · 原因”“手动完成”或
“等待手动结果”，不能统一显示成功勾选。

“补充结果”输入框包含：结果/判断、依据或链接、未确认事项；复现结果另提供环境、
操作/命令、预期、实际。定位与范围还包含建议修改位置、范围与验收条件。除主结果
外允许其余未知字段留空，不强制用户填写一份长报告。

```text
我来完成这个步骤
结果 / 判断       [必填]
依据 / 链接       [可选]
未确认事项        [可选]

[保存补充结果]     [提交为本阶段结果]
```

保存补充结果不会推进流程。提交为本阶段结果会校验完成条件，满足后记录人工完成，
否则保存材料并指出仍缺的具体内容，不丢失输入。定位与范围的最后操作可明确为
“确认范围并继续”，一次保存人工结论和范围决定，不要求先提交再在第二个节点确认。
继续的含义是推进到合法的下一阶段；是否自动派发继续沿用现有已授权目标和自动
编排。没有执行授权时只展示下一阶段操作，不因填写结果自动启动代码修改。

跳过使用紧凑表单，要求一句理由；预览目标阶段及仍待满足条件，再提交。
“跳过定位与范围的 Agent 调查”后仍必须填写并确认目标/范围/验收条件，不能把跳过
调查等同于范围已接受。PR 不会因跳过自动审查就直接合并或发布。

## 5. 不同步骤的允许边界

| 阶段 | 可跳过的内容 | 手动完成所需内容 |
| --- | --- | --- |
| 分诊 / 预检 | Agent 分类与摘要 | 类别、目标、基本变更范围；已有 CI/冲突状态未知仍保留未知 |
| 定位与范围 | Agent 调查；复现默认可选 | 人工判断、目标、范围、验收条件及明确接受；复现证据不是必填 |
| 修复 / 文档更新 | Agent 编辑 | 实际补丁及对应基线、作用范围；只有文字说明不能算修改完成 |
| 验证 | Agent 执行验证 | 命令、环境、结果及证据来源；人工声明与已核验执行分开 |
| 补丁审查 | Agent 自动审查 | 明确人工审查决定、针对的补丁/版本和未验证项 |
| 交付与跟踪 | 可改由用户操作 | 实际 PR/提交/发布链接及远端状态；不伪造远端成功 |

第一版必须落实分诊/预检、定位与范围的跳过和人工完成，以及各阶段保存补充结果。
其余阶段的“提交为完成”仅在现有产物/版本绑定规则能接受真实材料时启用；缺少
补丁导入或外部执行证据核验能力时，明确显示缺少什么，不能提供一个必定失败的
通用“完成”按钮。

跳过 AI 执行不等于免除交付条件。验证跳过后显示“未验证”，可以保存材料供最终
审核，但不产生验证通过状态。现有交付接口不支持带限制交付时，继续保留阻塞并
显示条件；本次不新增绕过验证、审批或发布绑定的通用豁免开关。

真实人工补丁若要接入自动验证，应复用隔离 worktree 与补丁冻结/指纹流程；为人工
产物显式记录来源，不能创建一个假装 Agent 已执行并测试通过的 Job。只涉及文本
判断的手动阶段不需要创建 worktree。

## 6. 运行中接管、等待和版本更新

- 保存补充材料可以在运行中进行，标明“供后续核对”；不声称正在运行的 Agent 已
  读取新内容。当前运行是否重新读取仍由现有上下文机制决定。
- 手动接管、跳过、提交人工完成必须先停止该阶段和自动编排的相关执行；复用现有
  取消及暂停机制，确认没有仍占用该阶段的运行后才能推进。取消失败时保留原状态。
- 停止旧运行不销毁其 worktree 或产物。旧 Agent 的迟到输出只进入历史，不覆盖
  人工决定、不再次启动下一步；现有 run identity / current guard 继续生效。
- 只处理这个阶段的相关等待。用户明确选择手动完成或跳过时记录这些等待为何结束；
  不能假装给旧 Agent 授了权限，也不取消其他阶段、其他运行或外部事项的等待。
- 提交带 expectedVersion、caseId、目标阶段、源版本及幂等请求 ID。重复点击不重复
  推进或派发；并发提交或 GitHub 更新返回明确冲突，保留输入供用户重新核对。
- 用户材料保留提交时的来源版本。Issue 内容、仓库基线、PR head 或范围变化后，
  旧材料保留为历史；需要用户重新核对，不能默认仍可用于审批。
- 编辑人工结果追加新记录，不覆盖原记录；影响已有补丁或已接受范围时，重新确认
  受影响的下游阶段，沿用已有失效与版本检查。
- 重新交给 Agent 通过显式“重新调查”操作；把人工材料及来源一并传入，不强迫
  重新复现，也不抹掉此前跳过或手动处理记录。

## 7. 最小实现范围

- 现有 IssuePlan/schema 与提示词增加复现策略，调整 planBlocker；同步普通 goal
  continuation 和 Orchestration，避免一个入口解锁、另一个入口仍然阻塞。
- 时间线投影对 Bug 的 investigate + 范围 decision 做局部聚合。保留原 phase、JobKind、
  Job ID 和尝试记录；最终补丁审查的 decision 不属于这次聚合。
- 合并节点保留内部当前子阶段与原节点 ID 映射；旧 localStorage 的选中阶段映射到
  合并节点，保留选中的执行尝试。历史记录按当时语义展示，不重写已完成事实。
- 在 ProcessingCase 增加可选人工处理/决议字段，通过现有事件日志保存来源、理由、
  材料及阶段处置，不新增一套数据库或并行状态管理。
- 新增小型 application 服务处理接管/补充/跳过/完成，统一校验、暂停和事务提交；
  两条协调路径复用同一处置结果和 next-action 检查，不各自维护一套跳过规则。
- 人工材料进入后续 Agent 的上下文；区分 user_reported / tool_executed，保留事实、
  假设和未验证项。文本引用不变成 shell 退出码、通过的测试或虚构执行日志。
- StagePanel 使用独立 ManualStepForm 和复现小区块；可用动作由服务端返回，
  历史周期、关闭事项、旧版本节点保持只读。
- 新事件/人工等待语义需要版本化时，使用现有 workflow definition 与升级机制作
  小型版本扩展；保留旧版支持、原事件与运行身份，不重新执行历史任务或批量改写报告。

建议先完成非执行类人工阶段与 Bug 合并节点，再接入人工补丁/外部验证的可信材料
适配。后者只扩大材料接入，不重新设计工作流和 worktree 管理。

## 8. 验收场景

1. 无 reproduction/expected/actual 的 Bug，目标/范围/验收已接受后能进入修复。
2. 勾选尝试复现但环境缺失，显示未复现与原因；能继续定位和确认范围，无自动重试。
3. 用户主动要求必须复现时遵守该条件，撤销后可以继续。
4. 调查结果返回后同一个“定位与范围”节点进入待确认，确认后才推进修复。
5. 用户直接提交人工定位与范围，不产生 Agent 调查成功记录；下游能读取人工材料。
6. 跳过调查但缺少范围时保存理由与材料，要求确认范围，不直接启动修复。
7. 接管运行中的调查后，迟到结果不能覆盖人工决定或再次派发下一步。
8. 保存补充结果不停止当前任务、不自动推进；接管后等待结果的状态能在重启后恢复。
9. 并发提交、重复点击、GitHub 更新时保持版本与幂等保护，并保留表单内容。
10. 跳过验证不会产生 passed，文本修复说明不会产生 patch，手动决定不会伪造发布。
11. 历史复现、人工记录和已接受产物保持可查看；旧选中节点与尝试能够迁移。
12. 两种自动继续机制得到一致的动作和阻塞原因，PR 与其他 Issue 类别无误合并。
