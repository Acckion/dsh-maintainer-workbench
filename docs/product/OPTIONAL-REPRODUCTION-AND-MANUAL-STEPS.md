# 可选复现、定位与范围合并、手动完成阶段

日期：2026-10-11（Asia/Shanghai）
基线：master `8e5c27b`
分支：`feat/manual-workflow-steps`
状态：已在本分支实现；复用现有事件、编排与 worktree 管理，不做大规模架构重构。

## 用户决定的优先级

跳过步骤、提交文字结果和选择手动完成，都是用户的明确决定。系统必须保存并执行，
后续 Agent、状态机和自动编排必须遵守，不得以信息不足、没有复现、缺少结构化字段
或证据不足为由拒绝推进、重新执行已跳过步骤，或要求用户再次批准同一个决定。

保留用户输入原文。Agent 可以在后续工作中说明未知事项，但不能擅自改写用户结论、
把人工完成改为未完成，或通过重复追问重新设置已被用户跳过的门槛。

阶段处置与执行事实分别记录：用户决定可以推进流程；未执行的测试仍记录为未执行，
没有实际补丁或远端操作时不生成虚构产物。跳过某阶段本身不会触发发布或合并；
后续实际操作继续遵守用户已授权的目标和范围。

## 1. 目标与现状

Bug Issue 默认流程改为：

分诊 → 定位与范围 → 修复 → 验证 → 补丁审查 → 交付与跟踪

复现是“定位与范围”内的可选活动，不再是默认必经节点或继续实施的必要证据。
用户可以不让 Agent 复现，也可以自己提供复现结果。定位允许依据源码、已有日志、
已有测试或维护者补充的信息形成判断；假设与已确认事实必须分开。

现有约束不只来自 UI：`planBlocker` 要求缺陷计划具有 reproduction/expected/actual，
`issueTaskGuidance` 要求建立复现与前后对比证据；`nextGoalStep` 和自动编排都使用这些
检查。实现时必须同步调整，否则改了节点名字仍会阻塞。非空 reproduction 目前只是
复现条件文本，也不能被当成“已经实际复现”的证明。

调查已经使用 investigate Job，范围确认使用 decision/accepted 和 IssuePlan，
自动编排调查完成后已有暂停并确认计划的逻辑。保留这些机制，通过展示聚合形成
一个用户步骤，不合并后台任务类型，不引入通用流程编辑器或新的执行引擎。

第一版只对 Bug Issue 合并上述两个节点。PR 的最终维护者确认不能被合并进补充
调查；其他类别保持原流程，但可以复用手动参与入口。

## 2. “定位与范围”的内容与完成条件

同一个节点分成两种状态：

- 调查中：展示进度；Agent 整理问题位置、判断依据及建议范围。
- 待确认：展示结论和可编辑范围；维护者确认目标、范围和验收条件后完成本节点。

默认 Agent 路径需要整理调查材料，再由维护者接受实施范围。Agent 调查结束不等于
用户接受范围。用户也可以直接提交文字结果或跳过本节点，这两种决定直接推进流程，
不再强制满足默认路径的材料要求。主操作由状态决定，不同时铺开所有操作。

```text
定位与范围                         待确认

定位结论
问题可能位于……
依据：源码……；维护者提供的日志……
判断状态：源码判断 / 已有运行证据 / 尚未确认

变更范围     [可编辑]
验收条件     [可编辑]

复现（可选）                 未尝试
[ ] 让 Agent 尝试复现
提供我自己的复现结果

[确认范围并继续]              执行详情  ···
```

这里的“未尝试”“未成功”“环境不满足”都是复现状态，不自动把整个节点标为阻塞。
如果缺失信息确实使目标或范围无法确定，应说明缺哪项决策信息；不把“没复现成功”
本身当成要求用户不断补充信息的理由。

默认路径继续提供目标、范围和验收条件的编辑与确认。用户选择跳过或提交人工结果
时，不强制补齐这些字段；结合用户指令和已有上下文继续。expected/actual 作为已知
问题描述保留，空值不构成机械阻塞。未知内容明确标记，不要求编造。

## 3. 可选复现规则

- 默认不安排主动运行复现；复用已提供的条件、日志与证据。
- 勾选“让 Agent 尝试复现”后，进行一次有边界的尝试；环境不可用、失败或预算耗尽
  时保存结果并继续定位，不自动无限重试或重新请求同一信息。
- 已有任务时间/步骤预算继续生效。复现尝试只占调查预算的一部分，需为源码定位
  留出预算；第一版使用内部限制，不增加复杂设置页面。
- 用户要求“必须复现后继续”时记录为明确的额外完成条件，作为用户要求生效，
  不成为所有 Bug 的默认策略。这个条件未满足时允许用户修改或撤销自己的要求。
- 手动结果可以声明成功复现，但标为“维护者提供”，不会生成 Agent 的工具执行记录。
- 回归测试、补丁验证是否需要运行仍依据验收条件及验证策略，不能因为复现可选就
  把未运行的验证改写成通过。

建议在 IssuePlan 增加可选策略字段 reproductionMode：omit / best_effort / required，
新计划默认 omit；未设置字段的旧计划按默认可选解释，不把非空旧文本解释成 required。
旧 reproduction 字段继续保留原有复现条件，实际复现状态来自执行或手动记录。

## 4. 三种手动参与方式

每个可操作的当前阶段在“更多”中提供：

1. 补充结果：添加自己的观察，Agent 可以继续，不终止当前运行。
2. 我来完成：停止本阶段 Agent 执行，保留已有材料，进入“等待手动结果”。
3. 跳过此步骤：结束本阶段，不再安排此阶段的 AI 工作，直接进入下一阶段。

跳过和手动完成不是同一结果。时间线分别显示“已跳过”“手动完成”或
“等待手动结果”，不能统一显示成功勾选。

“补充结果”以一个自由文字输入框为主，依据、链接、未确认事项等都是可选内容。
复现环境、命令、修改位置、范围和验收条件可以写在同一段文字里；结构化字段只作
可选辅助，不校验用户结论是否“足够”，不要求用户提交一份长报告。

```text
我来完成这个步骤
结果 / 判断       [必填]
依据 / 链接       [可选]
未确认事项        [可选]

[保存补充结果]     [提交为本阶段结果]
```

保存补充结果不会推进流程，后续 Agent 必须遵守其中的用户指令。提交为本阶段结果
则立即保存原文，记录人工完成并推进，不经 Agent 二次审查，不因缺少字段或证据退回。
定位与范围可用“提交结果并继续”，一次保存人工结论和阶段决定，不要求先提交再在
第二个节点确认。是否自动派发沿用用户已授权目标和自动编排；未授权的外部操作不会
因填写结果自动启动。

跳过操作允许直接提交，理由可选，不用必填表单或第二次确认增加门槛。提交后显示
“已跳过”，进入下一阶段；不会再次要求填写目标、范围、验收条件或补充复现证据。
用户明确决定跳过范围确认时也应遵守，不将这个决定伪装成正常确认路径的完成记录。
PR 不会因跳过自动审查就直接合并或发布。

## 5. 各步骤的手动决定与事实记录

所有当前步骤都提供跳过与文字结果提交。下表约定展示与来源记录，不设置人工完成的
额外材料门槛。

| 阶段 | 用户决定的效果 | 事实记录 |
| --- | --- | --- |
| 分诊 / 预检 | 跳过或接受人工结果后继续 | 未提供的类别、CI、冲突状态保留未知 |
| 定位与范围 | 跳过或接受人工判断后进入修复 | 原文、可选范围与验收条件、复现状态及人工来源 |
| 修复 / 文档更新 | 不再要求 Agent 编辑，继续下一阶段 | 人工完成决定与实际存在的补丁分别记录 |
| 验证 | 跳过或接受人工结果后进入审查 | 未执行 / 人工报告通过 / 工具执行通过分别展示 |
| 补丁审查 | 遵守用户审查结论或跳过决定 | 人工决定、对应版本和已知未验证项 |
| 交付与跟踪 | 接受用户决定，不重复代执行 | 用户报告与实际查询到的 PR、提交、远端状态分别记录 |

第一版即落实所有当前阶段的跳过、保存补充和文字结果提交。缺少补丁导入或外部
证据核验能力，不影响用户决定生效，也不禁用这些入口。

验证被跳过后显示“未验证”，流程仍能继续；人工声明通过则显示“人工报告通过”，
不会强制补做 Agent 验证。现有验证、范围确认等阶段检查必须识别用户处置，不能
在后续入口重新阻塞同一决定。实际操作需要实际对象，例如应用补丁需要补丁，
可以使用已有产物或用户提供的产物；缺少对象时说明具体操作暂无法执行，但不撤销
人工完成、不返回已跳过阶段，也不自行编造补丁、测试结果或远端成功。

真实人工补丁若要接入自动验证，应复用隔离 worktree 与补丁冻结/指纹流程；为人工
产物显式记录来源，不能创建一个假装 Agent 已执行并测试通过的 Job。只涉及文本
判断的手动阶段不需要创建 worktree。

## 6. 运行中接管、等待和版本更新

- 保存补充材料可以在运行中进行，标明“供后续核对”；不声称正在运行的 Agent 已
  读取新内容。当前运行是否重新读取仍由现有上下文机制决定。
- 手动接管、跳过、提交人工完成先保存用户决定，并撤销旧运行更新当前阶段的权限，
  再复用取消及暂停机制清理相关执行。取消失败不能撤销用户决定；显示执行清理状态。
  新的写入任务等待旧 worktree 写入占用释放，避免两个执行同时修改代码。
- 停止旧运行不销毁其 worktree 或产物。旧 Agent 的迟到输出只进入历史，不覆盖
  人工决定、不再次启动下一步；现有 run identity / current guard 继续生效。
- 只处理这个阶段的相关等待。用户明确选择手动完成或跳过时记录这些等待为何结束；
  不能假装给旧 Agent 授了权限，也不取消其他阶段、其他运行或外部事项的等待。
- 提交带 expectedVersion、caseId、目标阶段、源版本及幂等请求 ID。重复点击不重复
  推进或派发。阶段仍匹配的并发更新合并后接受决定；阶段已变更时保留输入并明确
  展示目标差异，不静默将决定应用到另一个阶段。
- 用户材料保留提交时的来源版本。Issue、基线、PR head 或范围变化后提示版本差异，
  不自动撤销用户决定、重跑已跳过阶段或重新要求同一输入。具体补丁和远端写入仍
  绑定实际目标版本，不能把旧产物冒充为新版产物。
- 编辑人工结果追加新记录，不覆盖原记录。用户新决定优先于旧决定；涉及已有产物
  时更新实际版本绑定，不自动添加材料完整性审查或重新确认全部下游阶段。
- 重新交给 Agent 通过显式“重新调查”操作；把人工材料及来源一并传入，不强迫
  重新复现，也不抹掉此前跳过或手动处理记录。
- Agent 不得自行重新打开用户已跳过或手动完成的阶段。用户明确重新打开、撤销跳过
  或修改要求后，才恢复对应 Agent 工作。

## 7. 最小实现范围

- 现有 IssuePlan/schema 与提示词增加复现策略，调整 planBlocker；同步普通 goal
  continuation 和 Orchestration，统一优先检查用户处置，避免一个入口解锁、另一个
  入口仍因缺字段、缺复现或未执行验证而阻塞。后续阶段与交付入口也遵守同一决定。
- 时间线投影对 Bug 的 investigate + 范围 decision 做局部聚合。保留原 phase、JobKind、
  Job ID 和尝试记录；最终补丁审查的 decision 不属于这次聚合。
- 合并节点保留内部当前子阶段与原节点 ID 映射；旧 localStorage 的选中阶段映射到
  合并节点，保留选中的执行尝试。历史记录按当时语义展示，不重写已完成事实。
- 在 ProcessingCase 增加可选人工处理/决议字段，通过现有事件日志保存来源、理由、
  材料及阶段处置，不新增一套数据库或并行状态管理。
- 新增小型 application 服务处理接管/补充/跳过/完成，统一目标绑定、暂停和事务提交；
  两条协调路径复用同一处置结果和 next-action 检查，不各自维护一套跳过规则。
- 人工材料进入后续 Agent 的上下文；区分 user_reported / tool_executed，保留事实、
  假设和未验证项，显式传入必须遵守的用户指令与阶段决定。文本引用不变成 shell
  退出码、通过的测试或虚构执行日志；上下文压缩后也保留用户决定及原文引用。
- StagePanel 使用独立 ManualStepForm 和复现小区块；可用动作由服务端返回，
  历史周期、关闭事项、旧版本节点保持只读。
- 新事件/人工等待语义需要版本化时，使用现有 workflow definition 与升级机制作
  小型版本扩展；保留旧版支持、原事件与运行身份，不重新执行历史任务或批量改写报告。

先实现所有阶段统一遵守用户处置与 Bug 合并节点，再按需扩充人工补丁/外部验证
材料适配。材料适配只扩大实际操作能力，不作为跳过和文字结果生效的前提，不重新
设计工作流和 worktree 管理。

## 8. 验收场景

1. 无 reproduction/expected/actual 的 Bug 能正常定位；用户跳过或提交文字结果时，
   即使范围或验收字段不完整，也能继续。
2. 勾选尝试复现但环境缺失，显示未复现与原因；能继续定位和确认范围，无自动重试。
3. 用户主动要求必须复现时遵守该条件，撤销后可以继续。
4. 默认 Agent 调查返回后同一个“定位与范围”节点进入待确认；用户可确认、跳过
   或提交文字结果继续，不生成第二个范围确认节点。
5. 用户直接提交人工定位与范围，不产生 Agent 调查成功记录；下游能读取人工材料。
6. 跳过定位与范围时理由可空、范围可空，直接推进；后续 Agent 不强制补填或重做。
7. 接管运行中的调查后，迟到结果不能覆盖人工决定或再次派发下一步；取消失败不
   撤销决定，新代码写入等待旧运行释放 worktree。
8. 保存补充结果不停止当前任务、不自动推进；接管后等待结果的状态能在重启后恢复。
9. 并发提交、重复点击、GitHub 更新时保持目标绑定与幂等保护，并保留输入和决定；
   不因普通同步自动重跑已跳过阶段。
10. 跳过验证仍能继续且不产生工具 passed；人工报告通过直接接受并继续。文本修复
    说明不产生虚构 patch，手动决定不伪造发布，但都记录相应阶段处置。
11. 历史复现、人工记录和已接受产物保持可查看；旧选中节点与尝试能够迁移。
12. 两种自动继续机制一致遵守用户决定，PR 与其他 Issue 类别无误合并。
13. 后续 Agent 不因认为用户输入不足而退回、不改写原文、不反复追问；只有用户明确
    改变决定时，才重新执行相关步骤。重启、重试和上下文压缩后仍保持此规则。

## 9. 实现与验证入口

- `application/manual-steps.ts` 处理阶段处置，`POST /processing/step` 提供统一接口。
- `workflow/manual.ts` 统一阶段映射、人工处置与后续上下文规则；现有事件引擎保存状态。
- `ManualStepForm` 提供文字输入、接管、跳过、提交结果及明确交回 Agent 的操作。
- `npm run check` 检查类型、单元测试和构建；`npm run test:browser:manual` 验证桌面
  与窄屏的接管、文字提交、跳过和历史查看。
- 文字结果用于人工阶段处置；实际补丁仍使用现有 worktree/产物，未增加任意路径的
  补丁导入接口。没有实际补丁时可继续手动流程，不创建虚构代码改动或验证运行。
