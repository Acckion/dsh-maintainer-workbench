# AI加开源参赛材料完善待办

整理日期：2026 年 10 月 24 日。对应报告：[开源维护智能工作台技术报告](../../output/docx/开源维护智能工作台技术报告.docx)，工程依据为 `93819a8`、插件版本 `0.4.0`。

当前报告已覆盖九章结构、分层架构、持续编排、结构化缺口、环境恢复、仓库维护与验证边界。提交前重点是补齐团队及资源事实、固定可访问成果；提升评审说服力的重点是完整案例和有依据的前后对照。以下均为待办，完成核验后再勾选，不能将建议直接当作已完成结果。

## 优先级与执行顺序

| 优先级 | 工作 | 完成标准 |
| --- | --- | --- |
| P0 提交准备 | 团队信息、资源与 AI 使用披露、成果访问、文件格式 | 消除必要信息占位，资料真实，链接可用，材料符合提交规范 |
| P1 效果证明 | 完整案例、前后对照、演示 | 评委可核对具体输入、人工介入、系统输出和最终状态 |
| P2 表达完善 | 正文取舍、参考资料、版式与一致性 | 贡献易读，细节可追溯，图文及视频对应同一版本 |

建议先选择完整案例，同时安排团队信息和资源核查；案例与对照完成后更新报告，再固定成果版本、录制视频并导出最终 PDF。完整案例及量化对照是本项目的强化建议，不是赛事规定的唯一验证形式。

## P0 团队信息与实际工作

- [ ] 填写封面团队名称、编号，核对作品名称及申报方向与报名系统一致。
- [ ] 填写各成员实际承担的设计、实现、调试、测试和材料工作，注明代表性成果及协作方式。
- [ ] 将“团队应审核”等原则性表述补为实际审核、修订、验证和来源核查记录；不凭提交数量推定贡献。
- [ ] 确认参赛、评审展示和拟开放成果所需的权属与授权，不在报告中代填未经确认的声明。
- [ ] 检查报告、截图、视频及其他评审材料，不出现学校名称、校徽与指导教师身份信息。

完成标准：团队占位信息已补齐，实际工作可核验，材料不泄露受限制身份或敏感数据。

## P0 模型配置与第三方资源披露

- [ ] 记录最终演示提供方、模型标识、使用日期及关键配置；不公开密钥、认证链接或私有会话全文。
- [ ] 分别说明产品中的模型推理、后端确定性规则，以及开发和报告编写中的 AI 辅助用途。
- [ ] 补充团队对 AI 生成代码、文字和图示实际做过的审核、修改、验证及来源与权利核查实例。
- [ ] 将资源清单中的“最终配置待填写”“条款待核验”等改为经过核验的事实，记录适用许可或服务条款来源。
- [ ] 对齐 package.json、package-lock.json、第三方通知与实际分发包；同步历史 Harness/Cordis 版本说明。
- [ ] 核查新增 semver、Markdown 渲染依赖及其他分发资源的 LICENSE/NOTICE、署名与再分发义务。
- [ ] 在资源清单中明确开放方式、合规状态、自主开发边界；第三方服务不按本项目许可证重新授权。

完成标准：资源与版本对应实际提交包，每项关键义务有核查依据，AI 使用说明描述实际工作，而非只有未来承诺。

## P0 可访问成果与复现入口

- [ ] 固定最终源码提交或版本标签，并同步报告、演示视频和安装说明。
- [ ] 提供评审期持续有效的仓库、程序包或受限访问链接，使用相应访问条件验证可达性。
- [ ] 写明安装启动、最短演示步骤、模型及 GitHub 配置方式、环境要求和已知限制。
- [ ] 在干净环境或新 profile 核验当前版本安装；旧宿主的安装试用不作为现版本完整兼容证明。
- [ ] 明确哪些代码、插件、工作流、测试与文档已开放，哪些采取受限提交或后续开放计划。

完成标准：评委能够定位同一版本成果，并按说明启动或复现核心流程。没有上游采纳记录时，不将潜在贡献写成已完成社区贡献。

## P1 一条完整案例

- [ ] 从已保存的文档事项或 PR 中选择一条具有清晰输入和验收条件的案例。
- [ ] 固定仓库、事项、代码版本、模型、环境及检查命令；标明人为构造回归与已有人工修订。
- [ ] 展示原始问题、系统计划草稿及维护者实际修改的内容。
- [ ] 展示确认后的阶段流转、人工介入、失败与恢复，保留首次和重试结果。
- [ ] 展示最终补丁、真实测试输出、审核结论和实际交付状态，附可访问证据或必要脱敏摘录。
- [ ] 说明达成的验收目标和未完成部分；停在最终审核就写到最终审核，不描述为已经发布或合并。
- [ ] 选择关键截图和日志，将案例整理为报告中的一到两页。

完成标准：读者能沿“输入—计划—确认—执行—验证—审核—实际交付状态”核对结论。PR #9 的 6/6 只证明对应范围测试通过，不能单独证明完整远端交付；635 项自动测试也不能替代模型效果评测。

## P1 有依据的前后对照

- [ ] 优先对比早期工作台与当前工作流，固定双方版本和同一任务条件。
- [ ] 比较目标与验收整理、阶段派发、缺口处理、环境恢复和最终审核定位方式。
- [ ] 如需量化，先定义并记录人工点击、填写、决定、恢复及模型请求次数，区分必要决定与重复操作。
- [ ] 记录环境预热、缓存、模型配置、失败重试及人工修订，避免把条件差异当成效率收益。
- [ ] 用一张表说明具体改进及对应记录；未测指标保持未知，不填提升百分比。
- [ ] 如引用 Harness 原生会话、Superpowers 等外部方案，核对指定版本或公开资料，并区分文档比较与实测结果。

完成标准：创新主张对应具体行为差异和证据，不停留在“自动生成计划”或功能数量对比；不宣称未经验证的算法首创、性能领先或普遍成功率。

## P1 演示与效果呈现

- [ ] 用同一完整案例设计 3—5 分钟演示，展示核心操作、实际结果、必要人工决定和开放成果。
- [ ] 根据实际记录补充耗时、Token、费用或用户反馈；无法取得的数据不估造成事实。
- [ ] 区分工程回归、脚本模型夹具、浏览器夹具和真实模型受控试用。
- [ ] 确认画面、旁白和报告对“完成”“通过”“交付”的表述一致，避免将历史结果展示为当前新执行。

完成标准：视频能演示实际可运行流程，结果与报告证据对应。小规模案例可以用于验证，不需要为了参赛虚构用户规模、企业试点或社区采纳。

## P2 报告表达与最终文件

- [ ] 减少正文中的内部字段、重复限制声明与细碎修复日志，把必要技术细节移至附录。
- [ ] 保留架构、核心编排与证据机制，将腾出的篇幅用于完整案例、对照和开放成果。
- [ ] 为关键图表注明来源、日期、版本和真实或夹具属性，检查正文引用一致。
- [ ] 将参考资料中的笼统描述补为可定位的官方规则、仓库版本及证据入口。
- [ ] 完善不超过 300 字的作品简介，覆盖问题、方案、实现、效果与开放成果；作品名不超过 20 字。
- [ ] 将最终技术报告导出 PDF，确认文件不超过 10MB；正文建议 15 页以内，附录按需提供。
- [ ] 导出 MP4，确认时长 3—5 分钟、文件不超过 300MB；总决赛 PPT 按晋级通知准备。
- [ ] 对最终 PDF 逐页检查中文、图表、分页、链接与隐私，实际打开全部成果链接。
- [ ] 在报名系统核对材料齐备及最终版本，保存提交回执；Git 提交不代表赛事平台提交。
