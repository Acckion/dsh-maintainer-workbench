# Maintainer Workbench：Issue / PR 工作流设计

日期：2026-09-26。状态：设计基线，首轮工作流实现已落地。具体实现、验证和保留范围见 [IMPLEMENTATION.md](./IMPLEMENTATION.md)；本设计中的长期目标不能直接当作已实现能力。

## 1. 产品目标与设计判断

服务对象是需要同时处理多个仓库的维护者。核心价值是让维护者快速知道：哪些事项需要关注、目前卡在哪里、已有何种证据、下一步由谁处理。AI 承担整理与执行，维护者保留需求取舍和交付判断。

当前功能以分诊、调查、修复、审查、文档五种任务组织，缺少事项生命周期、阶段交付物和明确交接。需要从“给 Agent 派五种提示词”转为“围绕一个维护事项积累证据并推进”。不要求所有事项经过同一套流水线，也不为每个阶段强制开一个新 Agent。

产品原则：

- 分诊解决去向，调查解决不确定性，实施解决已接受的目标，验证提供运行证据，审查判断变更风险。
- 任务完成、成果可用、维护者采纳、远端发布、PR 合并、Issue 解决分别记录。
- 结果先可见；只有需要判断或产生远端影响时进入决策队列。纯分析不一律要求点击“接受”。
- 共享已有调查和验证，允许直接实施清晰的小任务；不得因跳过页面而跳过必要的证据校验。
- 默认沿用 Harness 模型、权限和仓库约定；不要求用户为每个角色重新填写模型与提示词。
- 推断必须带依据和覆盖范围；资料不可访问、工具不具备与模型不确定是三种不同情况。

## 2. 参考流程及取舍

| 参考 | 已确认的做法 | 本产品采用的原则 |
|---|---|---|
| Kubernetes Issue Triage [1] | 新问题先分诊，区分待补充信息、支持请求、重复和已接受等处理方向 | 分类只是分诊的一部分，必须给出处理去向；标签名称沿用各仓库，不强加 Kubernetes 标签 |
| GitHub PR 草稿/待审 [2] | 草稿与准备审查是不同阶段 | 实施中的变更和请求正式审查的变更分别展示 |
| GitHub PR Reviews [3] | 评论、批准、请求修改具有不同含义，可结合代码所有者参与 | AI 发现、维护者决定、GitHub Review 分开，不把本地“接受分析”当作批准 PR |
| GitHub 分支保护 [4] | 合并可能依赖必要检查和审查，新提交可能使旧审查失效 | 合并条件以当前远端状态为准，所有结论绑定版本 |
| GitHub Issue/PR 关联 [5] | 关联体现实施进度，满足目标分支等条件的合并可关闭 Issue | 创建 PR 不等于解决 Issue，合并和实际关闭需要重新同步确认 |
| Copilot 任务委派 [6] | 可以从明确任务进入代码工作，再审查交付的变更 | 输入要包含目标与验收条件，执行与审查形成迭代闭环 |

以下阶段、阈值、数据模型与产品布局为我们的设计推导，不是上述产品提供的功能清单。借鉴流程概念不代表复制了其代码或提示词；后续代码复用另行记录版本和许可证。

## 3. 三层状态，避免“待审核”混用

### 3.1 事项状态：这件事到哪一步了

事项对应一个 Issue 或 PR，另保存其关联关系。远端状态是 GitHub 的事实；本地阶段描述我们的处理进度，不能替代远端状态。

Issue：待分诊 → 待补充 / 待决策 / 已接受 → 调查或实施 → 验证 → 关联 PR → 已解决。

PR：待预检 → 草稿中 / 待审查 → 待修改 / 待复核 → 待合并 → 已合并，或关闭未合并。

阶段允许回退、分支、跳过。阻塞单独记录原因、等待对象和解除条件，例如等待报告者、等待环境、等待权限、等待维护者。

### 3.2 执行状态：这次 Agent 运行怎么样

排队、执行中、等待权限、等待输入、成功、失败、取消。运行结束不证明问题解决。暂停等候不能显示成仍在忙碌，取消不能抹掉已有产物。

### 3.3 产物与决策：哪些成果能用、能发布

产物状态：有效、部分覆盖、已过期、格式无效。决策状态：待决定、采纳、部分采纳、退回。发布状态：未发布、发布中、已确认、结果待核对、失败。

例如“分析完成 / 检查未运行 / 回复待发布”是合法组合，不压缩成一个绿色“完成”。CI、代码审查、发布和远端合并均有各自的事实来源。

## 4. Issue 流程与阶段契约

类型专属的字段、阶段、决策、页面动作和验收条件见 [Issue 分类与分类型处理流程](./ISSUE-WORKFLOWS.md)。该细化方案仍含待实现能力，应与实现记录区分阅读。

| 阶段 | 输入与边界 | 必须交付 | 退出条件与下一步 |
|---|---|---|---|
| 接入与同步 | GitHub Issue、更新、讨论、既有标签与关联 PR | 当前快照、来源、同步时间、缺失范围 | 已获取关键资料；权限错误进入连接阻塞，不假装没有问题 |
| 快速分诊 | 标题正文、必要讨论、已有标签、缓存仓库摘要、重复候选摘要 | 简短摘要、类型、建议优先级、模块、信息缺口、处理去向与依据 | 自动完成本地分类；高不确定性转待决策或调查 |
| 补充信息 | 真正影响判断的缺口，已提问内容 | 一条聚合追问草稿、等待谁、恢复条件 | 发出追问后等待回复；信息到齐只重新评估受影响部分 |
| 接受与排期 | 分诊建议、维护目标、现有工作 | 是否接受、范围、优先级、负责人或暂缓原因 | 需求明确可直接实施；原因或影响不明则调查 |
| 调查 / 复现 | 明确问题、关联证据、版本和受控工作区 | 已证实事实、竞争假设、复现记录、影响范围、建议修复边界 | 证据足够进入实施；否则给最小下一实验或阻塞原因 |
| 方案确认 | 调查结果、需求约束 | 验收条件、范围、兼容性取舍、测试计划 | 小变更可随实施授权一次确认；架构/API 取舍先由维护者决定 |
| 实施 | 已接受目标、必要调查与约束 | 补丁、变更说明、验证产物 | 达到验收或明确部分完成；进入变更审查 |
| 发布与跟踪 | 维护者确认的补丁及报告 | 草稿 PR、远端链接、关联 Issue | 进入 PR 流程；同步到已合并和 Issue 关闭后才进入对应完成状态 |

分诊必须是轻任务：默认不创建 worktree、不安装依赖、不跑测试、不浏览完整代码树、不展开完整 PR diff。允许从受限的只读接口检索讨论与缓存摘要，不能仅靠提示词约束一个具有任意 shell 权限的 Agent。超过资料/时间预算就返回部分分诊和调查建议。

分诊输出示例：功能请求；P2 建议；涉及同步模块；需求缺少冲突处理规则；下一步“请维护者确定冲突策略”。不输出几千字代码评审。

重复检测分两级：分诊提出“疑似重复”，附共享症状/引用；调查才能证实共同原因。绝不因相似标题自动关闭。

优先级同时展示用户影响、发生范围和依据，不以模型自报置信度直接排序所有事务。潜在安全问题转入维护者专门处理队列，不自动向公开讨论附加敏感细节。

### 各类型的短路径

- 明确的文档错字：接受 → 文档修改 → 文档检查 → PR。无需先写根因报告。
- Bug 报告缺版本与复现：分诊 → 聚合追问 → 等待 → 调查。等待期间不反复启动 Agent。
- 清晰的局部 Bug：接受 → 实施任务内复现/修复/验证；不强制独立调查任务。
- 新功能：需求取舍和验收标准先确定；不把“没有旧版失败测试”当作无法实施。
- 使用问题：基于已有文档生成答案草稿，必要时形成独立文档改进建议。
- 已存在解决它的 PR：转向跟踪/审查现有 PR，避免创建第二套修复。

## 5. PR 独立流程

PR 页面主动作是“变更预检 / 审查变更”，不是“智能分诊”。预检用于决定审查的顺序和条件，不将 PR 再归入 Bug/提问分类。

| 阶段 | 工作及产物 | 分工 |
|---|---|---|
| 变更预检 | 固定 head/base SHA、目标分支、草稿状态、关联 Issue、变更规模、可见 CI、已有审查与冲突状态 | 系统获取事实，轻量模型总结意图与影响；缺资料明示未知 |
| 变更审查 | 分析 diff、周边调用、测试和仓库规范；给逐条缺陷、严重度、触发条件、路径行号与覆盖范围 | 审查角色只提出有证据的发现，不顺手改代码 |
| 处理发现 | 每条发现支持接受、需要更多证据、不适用、已解决 | 维护者可编辑、合并和批量采纳，不必整份报告全收全退 |
| 修改迭代 | 将采纳的问题交给实施角色，保留同一 PR/分支关系 | 有写权限且已授权时更新原分支；他人 fork 无权限时提供补丁，不强推 |
| 验证与复核 | 在新 head 上运行必要检查；逐项判断已解决、仍存在、无法验证 | 复用历史上下文但不沿用旧版本“通过”结论 |
| 准备合并 | 汇总 CI、必要审查、冲突、草稿状态及未解决讨论 | “可见检查已通过”与“GitHub 确认可合并”分别显示；权限不足时不猜测 |
| 合并后 | 同步最终状态、关联 Issue、必要发布/回归跟踪 | 首版跳转 GitHub 由维护者合并；以后再按仓库策略扩展 |

审查结论的标准是“发现了哪些可证实的问题，覆盖了哪里”，不是“AI 给出了多少条评论”。没有发现问题也是有效结果。

版本语义必须落实到工作区：读取 diff 用明确的 base/head 与比较规则；运行验证用 PR head，必要时验证与目标分支的合并结果，并标明实际测试的 SHA。不能在默认分支测试后宣称 PR 已验证。Fork、目标分支变化、force-push 都触发重新检查。

CI 失败单独启动“诊断失败检查”：先区分真实回归、基线失败、不稳定测试和环境问题。仅看到红色状态不足以决定修改。日志不可访问时请求所需权限或材料，不重复盲跑。

## 6. 能力角色与协作

| 用户能力 | 责任 | 不承担的责任 | 消费什么 / 交付给谁 |
|---|---|---|---|
| 分诊 | 快速分类、信息完整度、优先级建议、路由 | 深度代码调查、根因保证、修复 | 事项快照 → 维护者或调查 |
| 调查 | 解释原因与影响，做最小实验 | 产品取舍、无边界重构 | 分诊与问题 → 方案/实施 |
| 实施 | 完成已接受的行为或文档目标 | 自己批准发布、顺手修旁支问题 | 验收条件与证据 → 验证/审查 |
| 验证 | 执行相关检查，记录实际环境与结果 | 只信模型描述、将构建等同测试 | 指定版本与补丁 → 审查/维护者 |
| 审查 | 独立检查变更及其风险、跟踪发现 | 自己消除自己提出的问题并算已批准 | 固定 diff 与验证记录 → 决策/实施 |
| 发布 | 执行已授权远端动作并核对回执 | 模型临时扩大动作、自动合并 | 已确认产物版本 → GitHub 状态 |

这些是能力边界，不要求六个常驻 Agent。简单任务可在同一 Session 连续完成实施与验证；审查默认使用新上下文，读原始目标与证据而非只看作者自述。同一个模型的第二次调用不等于独立人工批准。

文档维护归为实施的一种类型，复用 PR 生命周期；保留“文档检查/修正”快捷入口，不单建一套发布机制。修复按钮更名为“实施变更”，对 Bug 显示“修复并验证”，对功能请求显示“实现需求”。

调查允许在插件独立实验目录写临时复现测试和构建产物，但不直接更改受维护分支；权限仍由 Harness 明确控制。只读调查和实验复现是两个能力等级，无法实验时如实返回阻塞。解决当前“只读导致不能复现、只能让修复再查一次”的断层。

## 7. 交接数据：不要把上一轮聊天全部塞给下一轮

每次产物保存：来源事项、版本键、输入快照、目标与排除项、事实/假设、证据引用、缺口、覆盖范围、下一步建议和执行记录。

按阶段提供结构：

- TriageReport：类别、模块、影响、紧急性、重复候选、缺口、route、routeReason。
- InvestigationReport：复现条件、预期/实际、根因证据或假设、影响路径、最小实验、建议方案。
- ChangePlan / ChangeSet：验收条件、范围、补丁摘要、分支与 SHA、关联产物版本。
- ValidationReport：环境、命令、退出码、输出引用、执行 SHA、基线/变更后结果、未执行理由。
- ReviewReport：findings 数组，每条独立 ID、位置、严重度、论据、处理状态；整体覆盖范围。
- PublicationReceipt：精确动作与内容摘要、授权记录、对应产物版本、远端 ID/URL、是否已确认。

不要继续让所有任务都返回 category、duplicateOf、responseDraft、tests 的同一份大 JSON。schemaVersion + 阶段类型做校验；尽可能使用宿主支持的结构化输出或结果提交工具，实际支持情况需验证。格式错误只重试结果整理，禁止因序列化失败重复实施代码或发布远端动作。保留原始输出，不补造缺失结论。

上下文由轻到重：仓库摘要/标签/约定缓存 → 与事项相关的文档与代码片段 → 调查所需完整工作区。下一阶段直接消费已验证证据，但在版本变化时检查其依赖，不盲信旧报告。

## 8. 版本、并发与失败恢复

- Issue 分诊键：正文/标题/相关讨论变化与规则版本；仓库无关提交不应触发全库重新分诊。
- PR 审查键：base/head、diff 范围、审查规则版本；CI 状态单独刷新，避免每次 CI 更新重新读全 diff。
- 人类反馈是输入：否定原因、范围修订和已解决发现必须进入下一次尝试。当前“退回后从头重跑”应改成“按反馈继续”。
- 同一对象同一阶段同一输入去重；新输入使旧结果过期，但不丢弃可复用证据。
- 多仓库有独立身份和工作区命名空间；调度共享资源预算，以仓库轮转避免大仓库占满队列。不同变更分支独立，同一目标分支写入串行。
- 网络重试复用检查点；模型格式重试只整理结果；环境失败先修环境；输入变更重新规划；超时显示停在哪一步及已有证据。
- 发出远端请求后网络中断时先核对远端回执，不能立即重发。批量发布逐条追踪，不承诺跨 GitHub 操作原子性。
- 发布前校验远端对象及补丁版本；授权只针对用户看到的具体动作。内容修改后重新形成可确认预览。
- 取消后保留本地未发布产物；不将“取消”误表示成回滚已发生的 GitHub 操作。

## 9. 操作界面与自动化边界

默认首页展示“需要你处理”：补充信息决策、需求取舍、待审查变更、阻塞与失败。次级入口是 Issue 队列、PR 队列、执行记录、仓库设置。数量需区分事项数和运行次数，避免重试把待办数放大。

Issue 详情：问题 → 分诊摘要 → 当前处理阶段 → 证据/关联 PR。PR 详情：变更意图 → 审查发现 → CI/测试 → 待处理讨论 → 当前发布/合并条件。使用统一时间线串联，不要求用户在多个 Agent 会话中找结论。

主按钮由状态决定：待分诊显示“快速分诊”；缺信息显示“查看追问”；待调查显示“调查原因”；范围明确显示“实施变更”；PR 显示“审查此版本”；已有发现显示“处理选中问题”。高级动作可展开，避免每个对象都平铺所有按钮。

默认自动：同步、差异检测、已启用仓库的新事项轻量分诊、本地产物更新、过期标识。默认需委派：深度调查、代码/文档修改及耗费较大的验证。远端动作采用一次性预览确认或维护者事先配置的明确规则；不要求在每一步机械重复确认。

批量操作必须展示逐项结果。简单标签建议可成组确认；架构决策、关闭/重复归并与重要公开回复逐项提供理由。默认没有“批量全部接受 AI 结论”的笼统按钮。

初次接入只需要选仓库并继承宿主配置。后台识别语言、构建和测试入口、指导文档、标签与代码所有者；推断不确定时显示来源并允许更正。高级配置收进“仓库策略”：自动分诊、执行预算、允许的自动动作、环境初始化。共享登录是当前约束，不包装成多账号能力。

## 10. 设计时的差距及落地顺序（历史基线）

已存在的基础：真实同步、按仓库隔离、独立工作区、五种任务、结果审核、回复/标签/草稿 PR 发布、部分重复派发与发布恢复逻辑。

已核对的关键差距：

1. `workbench.ts` 对已有本地克隆的分诊也准备 worktree；triage skill 允许深入读代码。应先改为受限轻量分诊，PR 单独预检。
2. `types.ts` 共用 Analysis 和统一 awaiting_review；需要拆产物类型与运行/事项/发布状态，迁移旧记录并保留历史可读。
3. `native-runner.ts` 将多类任务置为只读；调查实验和 PR 指定版本验证需要明确工作区/权限模型。
4. 当前一般以仓库同步 SHA 准备工作区；PR head/base 验证应成为独立路径，不能仅靠提示词提醒“说明局限”。
5. 退回意见未形成完整的结构化交接；缺少逐项审查发现和同 PR 迭代闭环。
6. 当前发布动作限 comment、labels、pr；完整 review threads、CI 诊断、负责人、关闭/重新打开、合并条件等尚不能宣称支持。
7. 当前结果格式修复解决的是容错；稳定产物协议及只重试汇总阶段仍需要实施。

实施包 A：明确分工。分诊去 worktree/无任意工具，PR 改预检入口；简洁分诊结构与去向，轻量结果不全部挤入待审核。验收：100 条批量分诊不克隆、不执行 shell，缺资料仍有可操作去向。

实施包 B：形成闭环。调查交付物传入实施、验收条件、实验工作区、PR 正确版本、验证证据。验收：选一个缺陷从调查到补丁与回归，后阶段无需用户重复输入上下文；不能复现仍如实标注。

实施包 C：维护协作。逐项发现、同 PR 更新、CI 诊断、过期处理、远端动作预览。验收：PR 更新后旧发现可复核，旧审批不能发布新补丁；网络重试不重复评论或创建 PR。

实施包 D：规模化。仓库公平调度、预算、自动规则、事件增量更新、跨仓库概览。验收：一个大仓库或失败任务不会阻塞其他仓库。

先完成 A+B 的可运行最短闭环，再扩展 C+D。负责人分派、自动关闭、自动合并、发布管理放后续；页面不要提前显示可执行占位入口。

## 11. 效果验证

先记录当前版本基线，使用相同仓库、相同输入和同一模型比较。选 Bug、功能、提问、重复、缺信息、文档及 PR 更新等真实案例，邀请维护者标注可接受下一步；评估样本不混入正常用户工作区。

关键指标：分诊建议采纳率、去向错误率、人工操作次数、重复读取/重复追问次数、每事项 token 与耗时 p50/p95、真正生成可审查变更的比例、证据缺失比例、审查误报率、阻塞可恢复率。保留模型配置及版本以便复现。

不把“模型返回 JSON”“任务成功率”“PR 数量”单独当成产品效果。自动化门槛以实测误报和维护者负担决定；当前不承诺固定秒数或准确率。

必须覆盖：新增讨论补足信息；有人已在修；Issue 关闭；PR 新提交；fork 无写权限；CI 失败/未知；测试环境缺失；格式失败；取消；发布响应丢失；跨仓库同号 Issue；用户修改计划；文档小改跳过调查；新功能没有旧版失败基线。
