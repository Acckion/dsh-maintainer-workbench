## 1. 观众看完应该记住什么

一句话：**开源维护智能工作台，让 AI 的分析、修改、验证和 GitHub 交付有清楚的范围、依据和进度。**

面向个人和小团队维护者。开场人物明确为“开源项目维护者”，可以同时是贡献者；其处境是注意力有限、事项分散、判断和跟进成本高。人物有能力维护代码，画面中的疲惫来自不断切换、核对与追踪。先让评委理解他为什么需要工作台，再用一个能听懂的支付回调案例说明处理过程。

全片突出三件事：

1. **能发现测试遗漏的场景。** 同一条支付通知重发，库存被再次扣减。
2. **能核对判断依据。** 发现能对应到输入、实际结果、源码和测试；维护者据此决定。
3. **能把工作交接回社区。** 结论评论、修复提交和对应检查都有真实落点。

自主设计的重点是维护流程、状态与版本约束、证据关联、恢复及交付交接。DeepSeek Harness 提供模型、工具、权限与会话；不把宿主或所调用模型说成团队自研。

### 与评分的关系

官方评分分别为问题与场景 15、创新与设计 20、AI 与开源融合 20、完成度及可验证效果 25、开放复用 15、材料表达 5。视频把最多时间给实际发现、修复、验证和交付；用具体机制解释自主贡献，用可访问仓库与安装文档体现复用。包装不挤占证据。

规则要求 MP4、3–5 分钟、300MB 以内，并展示功能、流程、效果和开放成果；评审材料不出现学校、校标及指导教师信息。2026-10-28 已重新读取[官网通知](https://www.aicomp.cn/tracks/tracks-5/4924.html)及其中[规则附件](https://www.aicomp.cn/wp-content/uploads/2026/08/%E9%99%84%E4%BB%B61_AIC%C2%B7AI%E5%BC%80%E6%BA%90%E7%AB%9E%E8%B5%9B%E8%A7%84%E5%88%99%E5%8F%8A%E4%BD%9C%E5%93%81%E6%8F%90%E4%BA%A4%E8%A6%81%E6%B1%820812.pdf)。

### 03:25–03:50：不使用 Issue 的等时替换

整个过程里，AI 的结论、真实测试和维护者的接受决定分别记录。查看记录时能分清，这是哪一轮修改、哪些条件得到验证、哪些结果已经发布。后续出现新版本或继续处理，原有记录仍然保留，维护者可以接着核对。

这段机制说明配实际阶段与执行记录回看，不制造版本失效或恢复成功的虚构场景。

### 03:50–04:20

AI 负责理解、调查、生成修改和验证。开源 Harness 提供 Agent、工具、会话和权限基础。我们在这之上实现维护阶段的组织、版本与证据的关联、等待恢复和 GitHub 交付，让维护者可以清楚地决定何时继续、何时退回、何时发布。

### 04:20–04:40

插件源码、安装说明和工作流文档可以在仓库中查看，验收案例也提供复现入口。我们希望把零散的维护动作，连接成有范围、有证据、可追踪的协作流程。

最后一句说完后保留 2 秒静止链接。片尾另放小字：“本片展示自建验收案例；更广泛任务效果仍需评估。”不旁白朗读整页说明。

## 5. 画面到底铺满还是居中

### 主答案

**真实操作尽量占满可用画幅，关键证据局部放大；机制说明再分栏。** 不全程使用小软件窗口加大片装饰背景。

| 画面形态 | 适用内容 | 构图规则 |
|---|---|---|
| A：接近全屏的真实界面 | 开始审查、维护者决定、修复、交付 | 占画面宽度约 92–100%；去掉桌面和无关窗口，初次出现保留产品与仓库上下文；字幕遮挡冲突时给底部留独立区域 |
| B：局部证据特写 | 输入输出、关键发现、两三行 diff、测试结果 | 先给整体位置约 1 秒，再连续推近到可读局部；文字在 1080p 成片上建议至少 28–32px；保持源码/命令来源标签 |
| C：左画面、右解释 | “8→6”意味着什么、证据关联、自主贡献 | 左侧约 2/3 为实际画面或说明示意，右侧约 1/3 放一句解释和一个关键数值；不是左右两段长文 |
| D：全屏简洁图卡 | 片头维护者场景、案例内库存示意、三层融合关系、片尾资源 | 图卡时间短；项目名、GitHub 地址清楚；避免伪装成可操作的产品页面 |

主线中真实界面及其特写约占 70–80% 时间。截图/录像缩放不改变内容，也不覆盖实际错误、失败或执行状态。

### 对现有原片的具体处理

- 13:21 原片 4096×2284，接近 16:9：适合保留整体开场、随后裁去无关宿主侧栏并推近主详情区。
- 18:37 原片 2996×2070，更接近 3:2：先保比例适配，再按镜头内容裁切；不要拉宽人物、字体或按钮。关键页面优先局部构图，不用大片黑边维持全部无关侧栏。
- 两种画幅交替时以同一块内容或按钮为视觉锚点，不让主对象忽左忽右。每次换页面先留定位时间，再推近。
- 已有界面步骤条在阶段交接处保留，让观众知道“现在到哪一步”；不必每个特写都带完整侧栏，也不另加一条始终占屏的重复流程条。
- 鼠标保留正常轨迹，删除来回寻找按钮、空滚动和重复点选。保留“点击→实际结果”的必要前后画面，通常各约 0.5–1 秒。
- 关键证据静止阅读约 4–7 秒，密集界面只露出本句旁白所对应的部分。不要边高速滚日志边要求观众读字幕。

## 6. 字幕、标题与视觉样式

风格：干净、克制、与深色原生界面一致。底色接近现有工作台，主文字高对比，蓝色用于流程/定位，琥珀用于待修订，绿色用于实际通过；同时保留明确文字，不能只靠颜色。

以 1920×1080 输出为例：

- 主标题约 64–72px；数字 10/8/6 约 90–120px；段落短标签约 34–40px。
- 配音字幕约 36–42px，最多两行，每行约 18–22 个汉字；按语义换行，不把“同一订单”“测试通过”等词拆开。
- 局部界面证据保持可读，旁注约 30–36px。安全边距左右约 80px，上下约 60px；最小角标也应在正常播放尺寸下可辨。
- 字幕使用窄半透明底板或适度描边，不用整块高遮挡黑框。位置可随证据移到上方或独立下沿，不能盖住结果、发布按钮或测试状态。
- 同屏最多一个主要结论、一个必要来源角标及字幕。无需同时出现阶段横幅、完整流程条、网址、滚动旁注和多处箭头。
- 全部自制图卡统一一种可合法使用的中文无衬线字体，英文字体也统一；保留字体、图标、音乐及配音来源登记。项目名按报名最终名称统一，当前文案沿用“开源维护智能工作台”。

长期角标只保留必要信息：“自建验收案例 · 预设缺陷”。真实操作首次出现时短暂注明“原生 App · 实际模型执行”；跳过等待时显示“等待已压缩”。说明图卡注明“案例示意”；另日补拍已保存结果时注明“结果回看”。这些角标不需要逐次配音。

## 7. 转场和动画

只使用以下几类，让镜头关系比特效更明确：

1. **直接切换：**同一操作的结果、报告到源码、工作台到真实 GitHub 页面。主体位置尽量匹配。
2. **短淡化：**跨时间、跨大段落时约 0.2–0.3 秒；不要每次点击都淡化。
3. **连续推近：**从完整界面进入报告、diff 或测试结果，约 0.4–0.7 秒，缓入缓出；不要连续来回抽拉。
4. **形状与关键词匹配：**片头分散的 PR 卡片收拢后，匹配切入真实 PR 列表；进入案例后，“重复通知”对应 PR 中同一约定，修复前“6”与验证后的“8”形成前后呼应。
5. **短阶段标签：**“发现问题”“核对依据”“修复验证”“交付跟踪”，每个大阶段最多一次，约 1–1.5 秒，叠在画面上，不另插全屏章节卡占时间。
6. **流程图逐步出现：**GitHub、Harness、工作台三层按旁白依次显现，边走边解释，最后停住约 3 秒。

不做粒子、旋转、翻页、3D 镜头、光标拖尾；不让每次点击都响。动画不把待完成节点自动变绿。核心发现与验证结果保留正常速度，不用高速播放掩盖。

## 8. 配音、音乐与节奏

- 语气像在带人看一个已经核对的工作过程，稳、清楚、有停顿。中英文术语首次只解释必要含义：PR 可称“代码贡献”，幂等解释为“同一通知重复处理也不再扣减”。不要求评委先懂 Git 或函数类型。
- 配音与操作分开制作，原片不需要边操作边讲；保持用户只交原片、后期统一完成的分工。
- 优先清晰人声。自然合成声也可作为候选，但需整段听读，修正 PR、Harness、幂等及数字读法，按适用条款使用并登记。
- 默认可以不加 BGM。若加，仅用轻微无歌词底乐，在旁白下明显压低；核对音源授权。不要用复杂节拍迫使证据镜头过快。
- 人声建议以约 -16 LUFS 综合响度为起点、真峰值不超过 -1 dBTP；按实际听感校正。播放设备换成普通笔记本扬声器再听一遍。
- 开头新事项进入可有两三次轻提示音，逐渐重叠后在工作台出现时安静下来；案例中的重复通知可另用一次轻提示。修复/通过无需庆祝音乐，片尾自然收束。
- 每 20–30 秒改变信息呈现方式：整体→特写→输出→人的决定→补丁→GitHub，避免同一静止页面长时间配解说。

## 9. “技术水平”具体怎么展示

不靠长代码或快速滚日志。保留三种能理解、也能检查的细节：

| 技术细节 | 给评委的解释 | 画面 |
|---|---|---|
| 重复通知与状态检查 | 同一付款重复送达，不能再次扣库存 | `order.status === 'paid'` 的最小差异，配“已处理则保留状态” |
| 回归测试 | 为这次发现补上能抓住重复扣减的用例 | 输入/重复调用/库存保持 8 的断言及真实输出 |
| 证据和版本关联 | 本次通过依据要对应本次修改 | 同一任务的执行记录、补丁，最后切到具体修复提交及其检查 |

最多让一段代码在屏幕上成为主角约 6–8 秒；不展开复杂持久化实现或全部模块图。没有真实机制演示时，版本约束与恢复作为产品设计说明，不把一张三层图当成机制已全部实测。

## 10. 素材选择与真实性约束

主片不采用：登录/密钥设置、模型参数、Token 调整、旧版 401/超时故障、来回找按钮、整个任务队列、所有菜单、多个类似 PR 的重复发现、长技术栈墙和长团队介绍。

真实素材不足时的替代原则：

- 远端结果已存在但没录到：可以补拍真实页面回看，注明“结果回看”，不伪造一次新的点击执行。
- 评论只显示预览：不说已发布；使用当前真实 GitHub 评论作为交付镜头。
- 修复已在分支但未合并：说“更新到原 PR”，不说“正式上线”或“社区采纳”。
- 修复前现有测试绿、修复后检查绿：分别锚定各自提交，不能拿最终绿灯冒充修复前证据。
- 原片有多轮尝试：时间压缩可以，素材按真实先后取舍；不能把早轮发现、晚轮结果包装成一轮零失败自动完成。不宣传“一次成功”。
- Issue #42 是新增功能；不用“修复去重 bug”的旁白。
- 四分四十秒是成片时长，不是 Agent 实际耗时。不使用未做公平测量的提效百分比、成功率、真实用户数量或竞品领先结论。

## 11. 开源融合与片尾具体放什么

| 层次 | 画面短文案 |
|---|---|
| GitHub | Issue / PR / 讨论 / 提交 / 检查 |
| DeepSeek Harness（复用） | Agent / 工具 / 会话 / 权限 |
| 维护工作台（本作品） | 阶段编排 / 版本与证据 / 恢复与交付 |

片尾建议：左侧真实仓库 README 与安装/文档区域特写，右侧依次三行“插件源码”“安装与复现”“许可与第三方说明”。最后保留项目名和 `github.com/Acckion/dsh-maintainer-workbench`。二维码可选，若使用需实测可扫；网址必须同时可读，不只有二维码。
