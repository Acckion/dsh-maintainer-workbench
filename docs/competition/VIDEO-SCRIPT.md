## 录制前约定

- 主流程全程使用同一个隔离的原生 Harness 环境和同一工作台版本。实际版本、模型、推理配置、费用上限、案例提交与证据位置在录制前登记；不把独立预览、夹具状态和真实执行剪成一次连续运行。
- 案例为自建的费用分摊小仓库：总额 10.00 元，3 人分摊，基线已复现预设算法产生 3.33、3.33、3.33 元，合计 9.99 元；目标为按约定顺序分配 3.34、3.33、3.33 元，合计 10.00 元。目标输出尚未由真实模型修复实现并验收，不能把基线复现当作通过。
- 角标明确区分“自建样例／预设缺陷”“真实模型运行”“实际测试输出”。预设被修复对象可以事先编写；模型过程与结果必须真实，不预定 AI 先错后对，不用 seed 生成的状态充当真实模型结果。
- 默认交付是**本地补丁导出**。无合格补丁时展示未交付和原因。GitHub 草稿 PR 只有在实际获得授权、完成发布并拿到回执后，才可等时替换第五段；不默认执行评论、标签或任何外部发布。
- 镜头名称描述要呈现的事实，不保证当前界面出现某个逐字按钮。录制前核对实际构建，从本地仓库维护目标进入；`ISSUE.md` 是自建任务说明文件，不代表真实 GitHub Issue。不将拟议待判断首页或新决策卡作为已实现画面。
- 等待允许加速或省略，画面标注“等待已加速／省略，实际用时见记录”；保留原始全过程与真实时间。不要为了连续感强行等待固定倍速，也不要倒置失败、修订和验收顺序。

## S1 · 问题｜0:00–0:20，20 秒

**镜头**：前 3 秒出现作品名；随后用自建案例的原始输入和复现结果展示“10.00 → 3.33 × 3 = 9.99”，少掉的 0.01 用简单标记突出。不要展示虚构的 GitHub 积压列表。

**配音底稿**：

> 十元分给三个人，每人三元三角三，合计却少了一分钱。这个自建分账样例带来一个维护问题：怎样找到原因，确定改动范围，再拿出让维护者能够放心核对的结果？

**字幕**：`自建演示仓库 · 预设缺陷`；`10.00 元 ≠ 3.33 × 3`。

**已备素材与待录分支**：[基线输出](../../artifacts/video-preparation/checks/baseline-demo.txt)与[基线测试](../../artifacts/video-preparation/checks/baseline-test.tap)可支持原缺陷画面；正式录屏须与登记的提交对应。图卡若未直接呈现命令输出，标“问题示意／基线已复现”，不能标成 AI 修复后的实际运行。

## S2 · 目标｜0:20–0:45，25 秒

**镜头**：打开同一事项的目标与范围。依次突出“分摊合计等于总额”“个人金额最多相差一分”“按约定顺序分配余数”；再显示允许修改的范围，由维护者确认。只露出支持决定的内容，不进入设置页。

**配音底稿**：

> 工作台围绕这条维护目标组织后续工作：分摊总额必须守恒，每人最多相差一分钱，余数按约定顺序分配。维护者确认修改范围和验收条件，再让 AI 继续。人的决定有明确对象，每一步都能回到最初要解决的问题。

**字幕**：`人确认：目标 · 范围 · 验收条件`；`期望：3.34 + 3.33 + 3.33 = 10.00`。

**先取得的素材与分支**：保存实际目标、范围、顺序约定与人工确认记录。若模型先提出资料问题，如实补充；不能用后期字幕暗示尚未确认的范围已获授权。输入与预期属于验收要求，不是修复成功证明。

## S3 · 实际执行｜0:45–1:45，60 秒

**镜头**：同一原生 Harness 中展示实际调查、允许范围内的执行与阶段记录。60 秒内只选三处可辨认画面：正在核对的代码位置、一次实际工具动作、阶段产物。等待压缩时保留事项、阶段和时间线标识；若实际有审批或补充输入，才短暂展示对应处理。

**配音底稿**：

> AI 在独立的仓库副本中工作，这次代码改动留在专用工作区。它先查看当前代码怎样计算金额，再围绕已确认的范围调查和修改。维护者看到的是一条持续的事项进度：现在做什么，已经留下什么结果，下一步由谁处理。需要深入时，可以打开对应会话和执行记录，不必在多个窗口里重新拼接上下文。遇到需要补充的资料或权限，过程会停在对应位置，等待明确处理。工作继续后，新结果和原有记录仍归属于同一事项，便于追踪。

**字幕**：`原生 Harness · 同一次真实模型运行`；出现剪辑时增加 `等待已压缩 · 实际用时见记录`。

**先取得的素材与分支**：本段指**未来待拍的真实模型执行**，本次目前仅有基线复现。需取得模型调用与执行记录、工具原始输出、模型与版本信息、环境及实际用时。首次成功就展示首次成功；实际失败或暂停就保留该结果，不导演先错后对，也不将预置成功状态接入。**尚未运行时，本段只能保留为待拍分镜，不能用 fixture 填满并标“真实运行”。**

## S4 · 证据｜1:45–2:35，50 秒

**镜头**：从当前结果进入对应改动，再打开一条实际测试的命令与输出。保留明确的输入、实际结果和状态，不长时间展示哈希或终端滚屏。最后停留在未验证范围。用局部放大帮助看清，避免配音逐个朗读技术字段。

**配音底稿**：

> 审核从当前修改开始。维护者先看改动与目标的对应关系，再打开实际测试，核对输入、输出和命令执行状态。十元分三人是否仍丢一分钱，其他人数和边界输入是否处理正确，都应有对应记录。工作台把模型报告、实际执行证据和审查结论放回同一事项，便于核对这份修改的依据。没有完成的检查继续显示为未验证，维护者可以根据结果决定是否还需要补充调查或修订。

**字幕**：`模型报告 ≠ 实际执行证据`；`当前改动 · 当前验证 · 未验证范围`。

**先取得的素材与分支**：同一基线与补丁的实际 diff、验证与审查来源、原始输出和覆盖限制。没有独立验证或审查时，不放对应“已通过”画面；直接标出缺失。若未生成补丁，可展示已有调查证据与未完成原因，不能借别次结果补齐。

## S5 · 人的决定与一种交付｜2:35–3:10，35 秒

**镜头**：维护者依据刚展示的证据作出实际接受或退回决定。合格产物进入本地补丁导出，并展示文件与对应版本；不合格则停留在退回或待补充状态。此处只展示一种交付路径，不巡游评论、标签、PR 菜单。

**配音底稿**：

> 最终决定留给维护者。依据不足就退回，条件满足才接受；本地接受与对外发布分开。交付可以选择导出本地补丁，保留对应版本和核验记录，交给维护者继续复核与使用。从目标到产物，每次决定都有清楚的对象，未完成的事项也继续保留。

**字幕**：`人决定：接受 / 退回`；实际导出时标 `本地补丁 · 未对外发布`，否则标 `未交付 · 原因见记录`。

**先取得的素材与分支**：人工决定与理由、补丁实际文件及导出记录。若界面无法走到导出，记录阻塞，不能制造按钮结果。实际通过并导出后，可将最后一句等时替换为：“这次已导出本地补丁，尚未向外部仓库发布。”只有实际获授权并完成 GitHub 草稿 PR 后，才能用真实回执替换本段默认补丁路径，且仍控制在 35 秒。

## S6 · 验收｜3:10–3:40，30 秒

**镜头**：同一案例的验收卡，逐项列出总额、金额差、余数顺序及约定边界输入；状态只来自实际结果。屏幕保留“单个自建样例”。如果基础 Harness 对照未执行，不出现改善比例、速度排行或成本下降箭头。

**配音底稿**：

> 最后回到验收卡，逐项核对总额、个人金额差和余数顺序，让每个结论都有对应结果。已经完成的要求、仍需补充的检查，一起交给维护者判断。这个自建样例展示的是一次处理过程，不能代表普遍修复效果。

**字幕**：`逐项验收 · 未测写未知`；`单个自建样例，不能代表普遍效果`。

**先取得的素材与分支**：按预先条件完成独立核对，并记录实际费用或明确未知。正式成片将前两句替换为下面**其中一条**实际结果句，最后一句单样例边界保留；配音不足或超时只调整停顿，不延长段落：

- 实际通过时：“这次实际分配为三元三角四、三元三角三、三元三角三，总额十元；其他验收条件与边界结果按卡片逐项标明。”
- 未通过或未完成时：“这次尚未达到交付条件。未满足的要求和原因列在卡片中，已有证据保留，后续可以据此继续处理。”

不得在未运行、未核验时提前选择“实际通过”分支。一次成功或失败都不是基础 Harness 对照的替代证据。人工查证、纠正和费用需同模型、同任务、同版本对照后再报告；本次没有这些结果就不制作提效、成本下降或成功率比较画面，无须在成片旁白中展开评测教学。

## S7 · 开放成果｜3:40–4:00，20 秒

**镜头**：作品名称、最终有效访问入口及三个可辨认资源名：“插件与安装说明”“资源与许可清单”“案例与复现记录”。保留一行“开放范围与未验证项见说明”。可用可复制短链接或二维码，录制前实际验证访问。

**配音底稿**：

> 我们希望小型开源项目更可靠地接住贡献，让维护者在关键点做判断。交付资料列出插件、安装说明、资源许可和复现记录，开放范围以清单为准。欢迎带着自己的任务核对它的价值。

**字幕**：`维护工作台 · 让判断有依据`；`有效入口与开放范围见交付清单`。

**先取得的素材与分支**：核对最终构建、可访问入口、[资源清单](RESOURCE-LIST.md)、[证据索引](EVIDENCE-INDEX.md)、[自建案例说明](../../artifacts/video-preparation/case/README.md)、案例许可与脱敏状态。尚未开放的资源明确标“待开放”，不能念作“已经公开可下载”；评审访问不等于社区采纳。
