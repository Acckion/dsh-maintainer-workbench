# 导演方案：片头介绍页配合完整台词

版本：2026-10-30，v5。固定4096×2284、30fps，整片目标290秒。新片头58秒；主体案例尚未按新表重剪。旧版文件保留。

## 1. 当前方向

先从开源维护者面对反馈与贡献的处境切入。20秒开始介绍产品，片头末尾用动画介绍页讲完完整段台词，再进入真实工作台。当前不是先显示真实界面再配总览，也不做代码/测试快速预告。

开源主线：社区反馈→AI与维护者推进处理→可核对的评论、补丁、测试与文档→回到社区并继续复用。

## 2. 片头怎么安排

| 时间 | 内容 | 处理 |
|---|---|---|
| 0—20秒 | 维护者、真实GitHub列表与卡片积压 | 沿用现有视觉和原音轨，不恢复左上/右上已删除的重复问题 |
| 20—25秒 | 原四张流程卡与项目名 | 开始新旁白，旧20秒后声音移除 |
| 25—30.7秒 | 新介绍页标题＋社区问题/代码贡献/仓库文档 | 由原卡片画面短淡化接入，保留统一配色 |
| 30.7—37秒 | 仓库检查、文档维护、按计划改进结构 | 一行统一能力说明，避免与三个对象卡片误对应 |
| 37—45.8秒 | 调查→修复→验证，查看进度/改动/依据 | 逐层呈现；此前信息略淡，重点落到当前介绍 |
| 45.8—52.47秒 | 结论与补丁→原帖与PR | 说明核对、复用、继续改进，不模拟已发生的发布 |
| 52.47—53.13秒 | 淡入真实工作台原图 | 只改变透明度，不缩放、裁剪或额外圆角 |
| 53.13—58秒 | 原图完整停留 | 原图100%、中心(2048,1142)，没有覆盖其上的卖点卡；旁白已结束 |

介绍页是概念说明，卡片不表示真实执行成功。所有新画面4096×2284，背景#0A1020。用户原图的既有边缘保留。

## 3. 当前旁白

这是基于开源 Harness 的 AI 维护工作台，面向个人和小团队的开源维护者。

社区的问题、代码贡献和文档，都能在这里统一处理。

除了处理反馈，还能检查仓库、维护文档，并在确认范围内改进代码结构。

面对一个 PR 或 Issue，AI 帮你调查、修复和验证。维护者查看进度、改动和依据，再决定是否发布。

确认后，把结论和补丁交回原帖与 PR，供社区核对、复用和继续改进。

“优化架构”收窄为“在确认范围内改进代码结构”，对应已有经确认的结构调整能力，不声称已独立验收自动架构优化。完整介绍声音20.25—52.12秒，使用本地Tingting临时合成；未发生模型API调用或麦克风录音。后续可沿同一时长换正式配音。

## 5. 各段怎样证明开源价值

PR41：测试通过仍有遗漏→AI实际复现10→8→6→评论回原PR→修复同时补回归测试→验证10→8→8→修复提交与对应CI。自建验收案例明确标注预设缺陷；不能混入PR40，也不说PR已合并或获独立上游采纳。

Issue：资料不足时提问留在原帖，让报告者和后来参与的人接着补充、定位。默认22；若用45新录屏，则原帖、分诊、发布和评论整段统一45。它们原帖相同，AI提问与评论可能不同，不说固定有四个问题。停在等待资料，不编造成已修复。

文档：README、开发指引、检查配置也属于社区贡献。真实功能截图用于说明入口与范围；没有执行录像时只说“可以”，不用虚构完成进度。

开源贡献说明：开源Harness/SDK提供工具与会话；社区审查工作流适配遵循Apache-2.0；自主实现维护阶段、依据关联和交付。原创插件代码MIT，开放源码、工作流、安装包、测试与文档，其他维护者可核对、安装和改进。

GitHub与模型API是外部服务，不统称开源；演示库当前未检测到许可证，不据插件MIT替其作授权声明。社区采用、效率提升与修复率需要真实测量，不写未经核实的数字。
